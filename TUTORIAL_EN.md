# Local Home AI with Open WebUI, Ollama & RAG — completely cloud-free

**Tutorial: A private AI assistant on your own LAN that can also search your own documents**

> Based on a setup by Matthias Kallenbach (LinkedIn post). Goal: a ChatGPT-like interface for everyone in the household ("Mom can use the home AI too"), where **no data ever leaves your own network**.

**Besides the tutorial, this repo contains the finished configuration files:**
[`docker-compose.yml`](docker-compose.yml) (Linux) · [`docker-compose.macos.yml`](docker-compose.macos.yml) (macOS) · [`.env.example`](.env.example) · [`nginx/`](nginx) (HTTP and HTTPS configuration) · [`scripts/`](scripts) (document sync, backup, Wake-on-LAN, systemd and launchd units)

The Docker host can be a **Linux machine with an NVIDIA GPU** or an **Apple Silicon Mac** — wherever the paths diverge, it's noted in the relevant section.

---

## 1. What are we building? (Architecture overview)

The setup consists of two machines and several services:

```
                        ┌─────────────────────────────────────┐
                        │  Docker host (Linux or macOS, 24/7) │
                        │  GPU: NVIDIA (CUDA) or Apple Silicon│
  LAN clients           │                                     │
  (browser, phone,      │  ┌───────────┐   ┌───────────────┐  │
   "Mom") ──────────►   │  │  NGINX    │──►│  Open WebUI   │  │
                        │  │  Reverse  │   └───────┬───────┘  │
  chat.heim.lan         │  │  Proxy    │           │          │
  ollama.heim.lan       │  │  (Port    │   ┌───────▼───────┐  │
  ollama-ws.heim.lan    │  │  80/443)  │──►│ Ollama        │  │
                        │  └─────┬─────┘   │ (Container,   │  │
                        │        │         │  GPU access)  │  │
                        │        │         │  + bge-m3     │  │
                        │        │         └───────────────┘  │
                        │        │         ┌───────────────┐  │
                        │        │         │ RAG pipeline: │  │
                        │        │         │ Docling +     │  │
                        │        │         │ bge-m3, index │  │
                        │        │         │ in Open WebUI │  │
                        │        │         │ (upload or    │  │
                        │        │         │  nightly run) │  │
                        │        │         └───────────────┘  │
                        │        │                            │
                        └────────┼────────────────────────────┘
                                 │
                        ┌────────▼────────────────────────────┐
                        │  Workstation (Windows or macOS)      │
                        │  Ollama "on demand" — only on        │
                        │  while the machine is running; for   │
                        │  larger models with a stronger GPU   │
                        └─────────────────────────────────────┘
```

**The components in detail:**

| Component | Role |
|---|---|
| **[Ollama](https://ollama.com)** | Local LLM server. Runs on the Docker host (Linux: as a container with a CUDA GPU; macOS: natively with Metal, see §3) **and** additionally "on demand" on the workstation (Windows or macOS). |
| **[Open WebUI](https://github.com/open-webui/open-webui)** | ChatGPT-like web interface for Ollama — with user management, document upload, and built-in RAG. |
| **[bge-m3](https://ollama.com/library/bge-m3)** | Multilingual embedding model (BAAI). Converts text into vectors — the foundation for document search (RAG). Very well suited for German (and other non-English languages). |
| **[Docling](https://github.com/docling-project/docling)** | Open-source tool from IBM Research: converts PDF, DOCX, PPTX, HTML, etc. into clean, structured Markdown/JSON — including tables and layout recognition. Runs either as a container or natively on the host; on Apple Silicon the native path is roughly twice as fast as the container in the 6-thread configuration shipped here (§7). (Written as "Dockling" in the original post — Docling is meant.) |
| **Open WebUI's vector store** | Vector database. Stores the embeddings generated by bge-m3 and returns the matching document snippets for a given question. It is already part of Open WebUI — no separate service, no separate container. |
| **[NGINX](https://nginx.org)** | Reverse proxy on the Docker host. Turns `http://192.168.x.y:11434` into nice, meaningful names like `http://ollama.heim.lan` — "no weird ports." |

**RAG** (Retrieval-Augmented Generation) means: before the language model answers, the system searches your own documents for relevant passages and feeds them to the model as context. This lets the home AI answer questions about your own PDFs, contracts, manuals, etc.

## 2. Prerequisites

**Hardware** (one of the two host variants):
- **Linux host:** A machine that runs continuously (mini PC, old desktop, home server), with an NVIDIA GPU with at least 4 GB VRAM. That's enough for small models (e.g. 3B–7B quantized) and embeddings. **But:** 4 GB is tight when the chat model and embedding model are needed at the same time — and that's exactly what happens with RAG. See "Realistic expectations with 4 GB VRAM" in §4.
- **macOS host:** An Apple Silicon Mac (e.g. a Mac mini) with at least 16 GB RAM. Thanks to unified memory, a large portion of RAM is available to the model as "VRAM" — a 16 GB Mac often handles RAG more comfortably than a 4 GB NVIDIA card. **Important:** Docker containers have no GPU access on macOS, so Ollama runs *natively* on the Mac (§3/§4).
- Optional: a workstation (Windows or Mac) with more GPU power for larger models "on demand."

**Software:**
- Docker + Docker Compose on the host → Linux: [Docker Engine](https://docs.docker.com/engine/install/); macOS: [Docker Desktop](https://docs.docker.com/desktop/setup/install/mac-install/) or [OrbStack](https://orbstack.dev)
- Linux host only: NVIDIA drivers + **NVIDIA Container Toolkit** (so containers can use the GPU) → [installation guide](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/install-guide.html)
- macOS host only: [Homebrew](https://brew.sh) for Ollama, NGINX, etc.
- On the workstation: nothing special — Ollama is available natively for Windows and macOS. (WSL2 only for the advanced path in §5 → [Microsoft docs](https://learn.microsoft.com/en-us/windows/wsl/install))

**Network:**
- The ability to assign local DNS names — realistically via **Pi-hole/AdGuard Home**, or as a fallback via a `hosts` file on the clients. A Fritz!Box alone *cannot* do this freely (details and options in §6, step 1).

## 3. Preparing the Docker host (GPU access)

### Linux (NVIDIA)

Install the NVIDIA Container Toolkit (Ubuntu/Debian, abridged — details at the link above):

```bash
curl -fsSL https://nvidia.github.io/libnvidia-container/gpgkey | \
  sudo gpg --dearmor -o /usr/share/keyrings/nvidia-container-toolkit-keyring.gpg
curl -s -L https://nvidia.github.io/libnvidia-container/stable/deb/nvidia-container-toolkit.list | \
  sed 's#deb https://#deb [signed-by=/usr/share/keyrings/nvidia-container-toolkit-keyring.gpg] https://#g' | \
  sudo tee /etc/apt/sources.list.d/nvidia-container-toolkit.list

sudo apt-get update && sudo apt-get install -y nvidia-container-toolkit
sudo nvidia-ctk runtime configure --runtime=docker
sudo systemctl restart docker
```

Test:

```bash
docker run --rm --gpus all nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi
```

If `nvidia-smi` shows the GPU, everything is ready.

### macOS (Apple Silicon)

On the Mac, the whole toolkit part is skipped — but a different basic rule applies: **Docker containers have no GPU access on macOS** (Docker runs there in a VM without Metal passthrough). Running Ollama in a container on a Mac would therefore be pure CPU torture. That's why only **Ollama natively** is installed on the macOS host (it uses the GPU via Metal automatically, with zero configuration), and everything else runs in containers:

```bash
brew install ollama
brew services start ollama    # starts Ollama as a service at every login
```

Install and start Docker Desktop (or OrbStack) — no further preparation is needed. The test here is simple:

```bash
ollama run llama3.2:3b "Say hello"    # responds promptly? Metal is working.
```

> ⚠️ **Unattended operation (24/7 host, e.g. headless Mac mini):** Unlike systemd services on Linux, on the Mac *all* the building blocks depend on a logged-in user session: `brew services start ollama` (without sudo) creates a LaunchAgent that starts on **login** — not on boot — and Docker Desktop/OrbStack likewise only run within a session. After a restart (power outage, update) without a login, the home AI is dead. So set this up once:
>
> 1. Enable **automatic login**: *System Settings → Users & Groups → Automatic login* (not possible with FileVault enabled).
> 2. Let **Docker Desktop/OrbStack start at login** (the "Start at login" setting).
> 3. **Disable sleep** — a sleeping Mac doesn't answer requests and doesn't run nightly jobs: `sudo pmset -a sleep 0 disksleep 0`. Also useful: `sudo pmset -a autorestart 1` (automatic restart after a power outage).
>
> The nightly jobs from §7/§11 also run as LaunchAgents in the user session for exactly this reason, not as root daemons.

## 4. Ollama + Open WebUI as containers

### Linux host

The finished [`docker-compose.yml`](docker-compose.yml) is in this repo; it's configured via an `.env`:

```bash
git clone https://github.com/fidel-karsto/local-ai-setup.git && cd local-ai-setup
cp .env.example .env      # adjust if needed (image versions, timezone, …)
docker compose up -d
```

The key points of the compose file (abridged — the file in the repo is the source of truth):

```yaml
services:
  ollama:
    image: ollama/ollama:0.33.1          # pinned instead of :latest — see "Updates" (§9)
    environment:
      - OLLAMA_KEEP_ALIVE=30m            # don't unload models from VRAM immediately
      - OLLAMA_MAX_LOADED_MODELS=1       # with 4 GB VRAM: only 1 model at a time
    volumes:
      - ollama-data:/root/.ollama
    ports:
      - "127.0.0.1:11434:11434"          # localhost only — NGINX (§6) is the LAN entry point
    deploy: …                            # GPU reservation, see file

  open-webui:
    image: ghcr.io/open-webui/open-webui:v0.11.1
    environment:
      - OLLAMA_BASE_URL=http://ollama:11434
    volumes:
      - open-webui-data:/app/backend/data
    ports:
      - "127.0.0.1:3000:8080"            # localhost only, see above
```

Both ports are deliberately **bound to `127.0.0.1` only**: from the LAN, access happens exclusively through the NGINX from §6 — so there's exactly one entry point. Ollama itself has no authentication whatsoever, so its vHost there sits behind an IP allowlist **and** basic auth (`satisfy all`); without both, there is no access to `/api/pull`, `/api/delete` and friends. (This also means `http://<docker-host-ip>:3000` will *not* work from other machines — set up §6 first and use `http://chat.heim.lan`, or for testing use an SSH tunnel: `ssh -L 3000:localhost:3000 <docker-host>`.)

Pull models:

```bash
# A small chat model that fits in 4 GB VRAM:
docker exec ollama ollama pull llama3.2:3b

# The embedding model for RAG:
docker exec ollama ollama pull bge-m3
```

**First login & registration:** On first launch, create an admin account. Then close open self-registration — otherwise anyone on the LAN can create an account: Open WebUI only reads `ENABLE_SIGNUP` from the `.env` on the very first start, after that the value comes from the database — so setting `ENABLE_SIGNUP=false` in the `.env` later and running `docker compose up -d` again has no effect. Instead, flip the self-registration toggle in the *Admin Settings*. Thanks to `DEFAULT_USER_ROLE=pending`, new accounts land on "Pending" anyway and must be approved individually by an admin.

**Realistic expectations with 4 GB VRAM:** `llama3.2:3b` (~2 GB) and `bge-m3` (~1.2 GB) each fit comfortably into VRAM individually — but with RAG, both are needed in quick succession (first the embedding of the question, then the answer from the chat model). With `OLLAMA_MAX_LOADED_MODELS=1`, the models take turns (short loading pauses per request); without that limit, some layers end up on the CPU (it works, but noticeably slower). `OLLAMA_KEEP_ALIVE=30m` at least prevents models from being unloaded again after just 5 minutes of idle time. Anyone who uses RAG regularly benefits significantly from more VRAM — or should deliberately compute embeddings on the CPU.

### macOS host

On the Mac, Ollama already runs natively (§3) — only the rest goes into containers. For this there's a dedicated compose file, [`docker-compose.macos.yml`](docker-compose.macos.yml): it contains no Ollama service and instead points to the Mac's native Ollama via `OLLAMA_BASE_URL=http://host.docker.internal:11434`:

```bash
git clone https://github.com/fidel-karsto/local-ai-setup.git && cd local-ai-setup
cp .env.example .env
docker compose -f docker-compose.macos.yml up -d

# Pull models directly, natively (no "docker exec" needed):
ollama pull llama3.2:3b
ollama pull bge-m3
```

The notes above on **first login & registration** apply unchanged. Instead of the VRAM gymnastics, the unified-memory rule of thumb applies on the Mac: macOS grants models roughly up to ~⅔ of RAM — on a 16 GB Mac, `llama3.2:3b` and `bge-m3` run comfortably side by side, and even 7B–8B models are feasible. If you want to set `OLLAMA_KEEP_ALIVE` or similar: `launchctl setenv OLLAMA_KEEP_ALIVE 30m` (followed by `brew services restart ollama`) takes effect immediately, but silently disappears again after a restart — for permanently wiring such variables, use a dedicated LaunchAgent instead of `brew services` — the bundled [`scripts/launchd/de.heim-ki.ollama-ws.plist`](scripts/launchd/de.heim-ki.ollama-ws.plist), however, no longer works as a template for this: it's now hardwired to the workstation role from §5 (`OLLAMA_HOST` fixed there to `127.0.0.1:11434`, for the SSH tunnel). For the Docker host, a simple copy of your own with a different `Label` and `OLLAMA_KEEP_ALIVE` in `EnvironmentVariables` is enough. And because Ollama natively listens only on `127.0.0.1` by default, the same security logic applies as on Linux: the NGINX from §6 is the only entry point from the LAN.

**Sources:**
- Ollama Docker image: https://hub.docker.com/r/ollama/ollama
- Open WebUI docs: https://docs.openwebui.com

## 5. Ollama "on demand" on the workstation (Windows or macOS)

The workstation typically has more GPU power, but doesn't run around the clock. That's why a second Ollama server runs there, available only when the machine is on.

### Windows: native app (recommended)

Install [Ollama for Windows](https://ollama.com/download/windows), then set `OLLAMA_HOST=0.0.0.0` as a *user environment variable* (`Control Panel → Environment Variables`) and restart Ollama so it's reachable from the LAN. Finally, open the port in the Windows firewall (PowerShell as administrator):

```powershell
# -RemoteAddress and -Profile matter: without them the rule applies on ANY
# network, even the "Public" profile — and Ollama has no authentication.
New-NetFirewallRule -DisplayName "Ollama" -Direction Inbound -LocalPort 11434 `
  -Protocol TCP -Action Allow -RemoteAddress <DOCKER-HOST-IP> -Profile Private
```

Done — no WSL, no port proxy, and Ollama starts automatically with Windows.

**Note on the bundled NGINX config:** the configuration from §6 assumes, for `ollama-ws.heim.lan`, the SSH-tunnel model from §5 (macOS) and hardcodes `proxy_pass` to `127.0.0.1:11435`. Anyone exposing the workstation directly like this instead has to change the `ollama-ws` server block by hand to `proxy_pass http://<WORKSTATION-IP>:11434;` — the firewall rule above (only `<DOCKER-HOST-IP>`, "Private" profile) then remains the only access barrier on the workstation itself.

### macOS: Mac as workstation

A Mac (e.g. a MacBook Pro with plenty of RAM) works just as well as an on-demand workstation. Ollama does **not** bind to `0.0.0.0` for this — Ollama has no authentication whatsoever, and bound to `0.0.0.0` the notebook would listen on every network it joins, including café or hotel Wi-Fi. Instead, Ollama stays strictly on `127.0.0.1`, and an **SSH reverse tunnel** exposes exactly that one port, in a targeted way, on the Docker host — there too only on its own loopback, where NGINX (§6) picks it up behind an IP allowlist and basic auth.

**1. Hardwire the local Ollama to loopback:** the bundled LaunchAgent [`scripts/launchd/de.heim-ki.ollama-ws.plist`](scripts/launchd/de.heim-ki.ollama-ws.plist) binds `OLLAMA_HOST` fixed to `127.0.0.1:11434` — nothing left to replace here:

```bash
brew install ollama    # just the binary — do NOT also run "brew services start ollama",
                       # or two instances will fight over port 11434

mkdir -p ~/Library/LaunchAgents /opt/heim-ki/logs
cp scripts/launchd/de.heim-ki.ollama-ws.plist ~/Library/LaunchAgents/
launchctl load -w ~/Library/LaunchAgents/de.heim-ki.ollama-ws.plist
```

**2. Generate a key pair for the tunnel** (on the workstation):

```bash
ssh-keygen -t ed25519 -f ~/.ssh/id_ollama_tunnel -N ""
```

**3. Record the Docker host's host key** — and check the fingerprint, otherwise something on the LAN could impersonate the Docker host:

```bash
ssh-keyscan <DOCKER-HOST-IP> >> ~/.ssh/known_hosts
```

Compare the fingerprint against `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` **on the Docker host**.

**4. On the Docker host**, create a dedicated, heavily restricted system account for the tunnel:

```bash
sudo useradd --system --create-home --shell /usr/sbin/nologin ollama-tunnel
sudo -u ollama-tunnel mkdir -p ~ollama-tunnel/.ssh
sudo -u ollama-tunnel tee ~ollama-tunnel/.ssh/authorized_keys <<'EOF'
restrict,port-forwarding,permitlisten="127.0.0.1:11435",permitlisten="172.17.0.1:11435" ssh-ed25519 AAAA... comment
EOF
sudo -u ollama-tunnel chmod 600 ~ollama-tunnel/.ssh/authorized_keys
```

`restrict` first disables everything (port, agent, X11 forwarding, PTY); `port-forwarding` is the only thing it turns back on — without this keyword the tunnel wouldn't come up at all, because `permitlisten` only restricts, it doesn't enable anything. The two comma-separated `permitlisten` entries limit the remote forward (`-R`) to exactly these two listeners: `127.0.0.1:11435` for NGINX (§6) and `172.17.0.1:11435` — the gateway address of the Docker bridge (`docker0`), through which Open WebUI (itself a container in the compose bridge network) reaches the workstation directly, without NGINX and without credentials, since a request from there would carry the bridge IP and fail the allowlist (403), and Open WebUI sends bearer tokens rather than basic auth for Ollama connections anyway (401); this second address is host-dependent — check it on the Docker host with `ip -4 addr show docker0` and adjust it here and in the `-R` line of the tunnel plist if it differs. `nologin` is unproblematic because `ssh -N` never starts a shell.

**Residual risk:** `port-forwarding` re-enables every forward type, including local (`-L`) and dynamic (`-D`) forwards — `permitlisten` only restricts the remote listener, not the forward direction. A compromised tunnel key therefore still allows pivoting from the Docker host; there is no per-key option in `authorized_keys` that closes this. Anyone who wants to close it as well can optionally add to the Docker host's `sshd_config`:

```
Match User ollama-tunnel
    GatewayPorts clientspecified
    AllowTcpForwarding remote
    PermitListen 127.0.0.1:11435 172.17.0.1:11435
    AllowAgentForwarding no
    X11Forwarding no
    PermitTTY no
```

`AllowTcpForwarding remote` is the first-class mechanism that allows exactly `-R` and excludes `-L`/`-D`, and like the rest of this block remains optional extra hardening against the pivoting risk; `GatewayPorts clientspecified`, however, is not optional once the second listener is in use — by default sshd silently binds remote forwardings to loopback and ignores a differing `bind_address` in `-R`, with no error, so the bridge listener would simply be missing. Anyone who doesn't want to add the Match block above still has to set `GatewayPorts clientspecified` for the `ollama-tunnel` user somewhere (globally, or in a smaller Match block of its own).

**5. Install the tunnel agent on the workstation** ([`scripts/launchd/de.heim-ki.ollama-tunnel.plist`](scripts/launchd/de.heim-ki.ollama-tunnel.plist), replace `DOCKER-HOST-IP` and `BENUTZER` in the file first):

```bash
mkdir -p ~/Library/LaunchAgents /opt/heim-ki/logs
cp scripts/launchd/de.heim-ki.ollama-tunnel.plist ~/Library/LaunchAgents/
launchctl load -w ~/Library/LaunchAgents/de.heim-ki.ollama-tunnel.plist
```

**6. Behavior when the notebook is absent:** if the Mac is off or away, the tunnel isn't up — `ollama-ws.heim.lan` then answers with `502 Bad Gateway`. That's intentional, not a failure.

**Beware of sleep:** A closed MacBook goes to sleep — and a sleeping Mac doesn't answer Ollama requests. For workstation use, disable sleep while on power (*System Settings → Energy*, "Prevent automatic sleeping") or use `caffeinate`.

### Windows alternative for advanced users: WSL2

If you'd rather run Ollama inside WSL2 (Ubuntu):

```bash
curl -fsSL https://ollama.com/install.sh | sh
```

For Ollama to also be reachable from the LAN (not just localhost), it must bind to all interfaces:

```bash
# In WSL, e.g. in ~/.bashrc or as a systemd override:
export OLLAMA_HOST=0.0.0.0:11434
ollama serve
```

Additionally, Windows must forward port 11434 into the WSL VM (PowerShell as administrator; find `<WSL-IP>` with `wsl hostname -I`):

```powershell
netsh interface portproxy add v4tov4 listenport=11434 listenaddress=0.0.0.0 connectport=11434 connectaddress=<WSL-IP>

# -RemoteAddress and -Profile matter: without them the rule applies on ANY
# network, even the "Public" profile — and Ollama has no authentication.
New-NetFirewallRule -DisplayName "Ollama WSL" -Direction Inbound -LocalPort 11434 `
  -Protocol TCP -Action Allow -RemoteAddress <DOCKER-HOST-IP> -Profile Private
```

**Pitfalls of the WSL path:**
- The WSL IP **changes on every Windows restart** — the `portproxy` then points into thin air and must be reset (e.g. via a scheduled task script). More elegant: on Windows 11 22H2+, enable *mirrored networking* in `.wslconfig` (`networkingMode=mirrored`), then WSL shares the Windows IP and the port proxy becomes unnecessary entirely.
- `ollama serve` in a terminal is **not a service** — close the terminal, Ollama is gone. For persistent operation in WSL, set up a systemd service (enable systemd in `/etc/wsl.conf`; the install script already creates an `ollama.service` — set `Environment="OLLAMA_HOST=0.0.0.0:11434"` there as an override).

## 6. NGINX reverse proxy: friendly names instead of ports

The clever part of this setup: instead of IP addresses and ports (`192.168.1.10:3000`, `:11434`), you get clean names on the LAN. For this, an NGINX runs directly on the Docker host — install it if it's not already there:

```bash
# Linux (Debian/Ubuntu):
sudo apt install nginx

# macOS:
brew install nginx
```

(The `sites-available`/`sites-enabled` scheme used below is Debian/Ubuntu-specific. On other Linux distributions, place the configuration in `/etc/nginx/conf.d/heim-ki.conf` instead. **macOS/Homebrew:** copy the configuration to `/opt/homebrew/etc/nginx/servers/heim-ki.conf` and start NGINX as root, because ports 80/443 are privileged: `sudo brew services start nginx`. Test/reload: `sudo nginx -t && sudo nginx -s reload`.)

NGINX then proxies:

| Name | Target |
|---|---|
| `chat.heim.lan` | Open WebUI (port 3000) |
| `ollama.heim.lan` | Ollama on the Docker host (port 11434) |
| `ollama-ws.heim.lan` | Ollama on the workstation (on demand) |

**Step 1 — DNS:** All three names must point to the IP of the Docker host. (`ollama-ws.heim.lan` also points to the Docker host — NGINX then forwards to the workstation. This way the configuration stays in one place.)

> ⚠️ **A Fritz!Box alone is not enough for this.** It only assigns names in the `<device-name>.fritz.box` pattern and supports neither custom domains like `heim.lan` nor multiple names (CNAMEs) for the same IP. Realistic options:
>
> 1. **Run Pi-hole or AdGuard Home** on the LAN (e.g. as another container on the Docker host) and enter the three names under *Local DNS Records* pointing to the Docker host's IP; then set Pi-hole/AdGuard as the DNS server in the router. The cleanest solution — and blocks ads on the side.
> 2. **A `hosts` file on every client** (Windows: `C:\Windows\System32\drivers\etc\hosts`, Linux/macOS: `/etc/hosts`): three lines with `<docker-host-ip> chat.heim.lan ollama.heim.lan ollama-ws.heim.lan`. Works immediately, but scales poorly — practically impossible on smartphones.
> 3. **Compromise without extra software:** Name the Docker host e.g. `chat` in the Fritz!Box — then the household reaches Open WebUI at `http://chat.fritz.box` (for this, add `server_name chat.fritz.box;` in the NGINX configuration, or work as `default_server`). The two Ollama API names are then unavailable; anyone who needs the APIs directly uses `<docker-host-ip>:port`.
> 4. **macOS host: no DNS at all (mDNS/Bonjour)** — see below.

> ℹ️ **Some routers are even more restrictive.** A Telekom **Speedport Smart 3**, for instance, knows no custom DNS entries whatsoever — neither A records nor an exception list; assign your own device names there and it switches local name resolution off entirely. The "fixed DNS servers" under *Internet → Internet connection* are a different thing, that is only the upstream resolver. What remains is option 1, 2 or — on a Mac — option 4.

**The comfortable route on a macOS host: `.local` instead of `heim.lan`**

If the home AI runs on a Mac, the chat needs **no DNS setup at all**. Two things play together:

- macOS announces its local hostname on the LAN automatically via **Bonjour/mDNS**. The machine is therefore reachable at `<local-hostname>.local` without a router entry and without a `hosts` file.
- NGINX uses the **first** server block on a listen socket as the *default server*. In [`nginx/heim-ki.conf`](nginx/heim-ki.conf) that is the chat vHost — so every name that matches no `server_name` ends up at Open WebUI.

Together that means `http://<name>.local` leads straight into the chat. A shorter name is set with

```bash
sudo scutil --set LocalHostName heim-ki     # afterwards: http://heim-ki.local
```

(the same is available under *System Settings → General → Sharing → Local hostname*). From a client you can check it with `ping heim-ki.local`, or in more detail with `dns-sd -G v4 heim-ki.local` (macOS) or `avahi-resolve -n heim-ki.local` (Linux).

Three limitations worth knowing:

- **Chat only.** The two Ollama vHosts really do check their `server_name` — `ollama.heim.lan` still needs real DNS or a `hosts` entry. For everyday browser use that is no loss.
- **Android is the weak spot.** macOS, iOS, Windows 10+ and Linux with Avahi resolve `.local` out of the box; Android browsers only do so unreliably — there the IP address remains.
- **With HTTPS (§10) the certificate will not match** unless the name is in it. So include the `.local` name in the mkcert call right away: `mkcert chat.heim.lan ollama.heim.lan ollama-ws.heim.lan heim-ki.local`.

**Step 2 — NGINX configuration:** The finished configuration is in this repo at [`nginx/heim-ki.conf`](nginx/heim-ki.conf) — before copying, replace `<LAN-CIDR>` with your own home network (e.g. `192.168.1.0/24`). The key blocks (abridged):

```nginx
# Open WebUI
server {
    listen 80;
    server_name chat.heim.lan;

    # Document upload (RAG): NGINX's default 1 MB limit isn't enough for PDFs
    client_max_body_size 100M;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        # WebSockets for the chat stream:
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_read_timeout 300s;
    }
}

# Ollama API (Docker host) — workstation block analogous, see file (proxies
# there to 127.0.0.1:11435, the SSH tunnel's target port from §5)
server {
    listen 80;
    server_name ollama.heim.lan;

    # Ollama comes with NO authentication of its own — hence an IP allowlist
    # AND basic auth (satisfy all = both are required, not just one of them):
    satisfy all;
    allow <LAN-CIDR>;
    deny  all;
    auth_basic           "Heim-KI Ollama";
    auth_basic_user_file /etc/nginx/heim-ki.htpasswd;

    location / {
        proxy_pass http://127.0.0.1:11434;
        # Don't pass credentials on to Ollama — it can't do anything with them
        # and would only log them:
        proxy_set_header Authorization "";
        # Depending on version, Ollama rejects foreign Host headers as
        # protection against DNS rebinding (403) — so send localhost, not $host.
        # Defensible ONLY because the auth_basic above sits in front of it:
        proxy_set_header Host 127.0.0.1:11434;
        proxy_read_timeout 600s;   # large models need time
        proxy_buffering off;       # token streaming
    }
}
```

**Create the basic-auth password file:** the Ollama vHosts above require basic auth in addition to the IP allowlist — set up a password file once for this:

```bash
# Linux (Debian/Ubuntu):
sudo apt install apache2-utils   # package providing htpasswd (Debian/Ubuntu)
sudo htpasswd -c /etc/nginx/heim-ki.htpasswd heim-ki
sudo chown root:www-data /etc/nginx/heim-ki.htpasswd
sudo chmod 640 /etc/nginx/heim-ki.htpasswd

# macOS: htpasswd is part of macOS's built-in (deprecated) Apache and already
# lives at /usr/sbin/htpasswd — no Homebrew package needed. NGINX runs as
# root here (see "sudo brew services start nginx" further below), so keep
# ownership/mode correspondingly tight; there is no www-data-equivalent
# group on macOS:
sudo mkdir -p /opt/homebrew/etc/nginx
sudo /usr/sbin/htpasswd -c /opt/homebrew/etc/nginx/heim-ki.htpasswd heim-ki
sudo chown root:wheel /opt/homebrew/etc/nginx/heim-ki.htpasswd
sudo chmod 600 /opt/homebrew/etc/nginx/heim-ki.htpasswd
```

⚠️ **For this HTTP variant only:** basic auth transmits the password base64-encoded in plain text, on every request — any device sniffing traffic on the LAN then knows it. Set up §10 (HTTPS) for permanent operation; this file is meant as an intermediate step before the mkcert setup.

**Windows workstation:** before `nginx -t`, replace `proxy_pass http://127.0.0.1:11435;` with `proxy_pass http://<WORKSTATION-IP>:11434;` in the `ollama-ws.heim.lan` block — the tunnel port above only applies to the macOS path from §5; Windows has no tunnel equivalent.

Install and enable:

```bash
# Linux (Debian/Ubuntu):
sudo cp nginx/heim-ki.conf /etc/nginx/sites-available/
sudo ln -s /etc/nginx/sites-available/heim-ki.conf /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx

# macOS (Homebrew):
sudo cp nginx/heim-ki.conf /opt/homebrew/etc/nginx/servers/

# Adjust the placeholder and the Linux paths in the COPIED file (fill in your
# own home network; under Homebrew the htpasswd file lives elsewhere than on
# Debian):
sudo sed -i '' \
  -e 's|<LAN-CIDR>|192.168.1.0/24|g' \
  -e 's|/etc/nginx/heim-ki.htpasswd|/opt/homebrew/etc/nginx/heim-ki.htpasswd|g' \
  /opt/homebrew/etc/nginx/servers/heim-ki.conf

sudo nginx -t && sudo brew services restart nginx
```

> **If the placeholder stays in place**, the configuration test aborts right away — `allow <LAN-CIDR>;` is not a valid directive:
>
> ```
> nginx: [emerg] invalid parameter "<LAN-CIDR>" in .../heim-ki.conf:<line of the allow directive>
> ```
>
> NGINX then refuses to load the **whole** file, the chat vHost included. That is why `nginx -t` comes before the start here, just as in the Linux line, and not after it.

> **Two warnings during `sudo brew services start`** are normal, not errors: "Taking root:admin ownership of some nginx paths" only means a later `brew upgrade nginx` will need `sudo` as well. And "`nginx` must be run as non-root to start at user login!" is actually what you want here — as a root **LaunchDaemon**, NGINX starts at *boot* rather than at login, which makes it the only piece that survives a restart without anyone logging in (Ollama and Docker Desktop still depend on a session, see §3). Root is mandatory anyway, ports 80/443 are privileged.

The configuration itself is identical on both systems — Open WebUI listens on `127.0.0.1:3000` and Ollama on `127.0.0.1:11434`, regardless of whether Ollama runs in a container (Linux) or natively (macOS).

**If Ollama returns `403 Forbidden` through the proxy:** That's Ollama's protection against foreign Host/Origin headers. The configuration above already works around this (`proxy_set_header Host 127.0.0.1:11434;`). `OLLAMA_ORIGINS=*` would also fix it, but it's a bad idea: it lets any web page anyone in the household opens send requests to the API. Working around the host check is only defensible here because the allowlist and basic auth sit in front of it in NGINX.

Now both Ollama APIs are reachable on the LAN under proper base URLs — for humans and CLI clients, that means entering `http://ollama.heim.lan` in Open WebUI under *Admin Settings → Connections*. That does **not** hold for the workstation: Open WebUI itself runs as a container in the compose bridge network, so a request from there to `ollama-ws.heim.lan` would carry the bridge IP instead of a LAN address (403 at the allowlist), and even with an allowed IP, Open WebUI sends bearer tokens instead of the basic auth NGINX expects for Ollama connections (401) — so the vHost stays reserved for human and CLI clients. For the workstation, enter `http://host.docker.internal:11435` instead, which is exactly what the second tunnel listener from §5 provides on the Docker bridge gateway address (`extra_hosts` in `docker-compose.yml` makes the name resolvable inside the container). If the workstation is off, you simply use the Docker host's models.

To check that this path actually works, query it from inside the container — that's exactly the perspective Open WebUI accesses it from:

```bash
docker exec open-webui curl -sS http://host.docker.internal:11435/api/tags
```

If the workstation's model list comes back, everything is fine. A connection error almost always means the bridge gateway address from §5 is wrong on this host (check with `ip -4 addr show docker0`), or the tunnel isn't running.

**Tip:** Anyone who'd rather click than write config files can use [Nginx Proxy Manager](https://nginxproxymanager.com) as a container.

**Source:** NGINX reverse proxy docs: https://docs.nginx.com/nginx/admin-guide/web-server/reverse-proxy/

## 7. Setting up RAG: Docling + bge-m3 + Open WebUI

Now for the part that "grinds through everything at night": documents are converted to clean text with Docling, turned into vectors with bge-m3, and stored in Open WebUI's vector store.

Two roads lead there, and they don't exclude each other:

- **Variant A** — upload documents through the browser, with Docling running as a container. The simple route, and the right one for most people.
- **Variant C** — a folder on the host is synced automatically every night, with the conversion running *natively* on the host. The result lands in the same kind of knowledge collection as in Variant A.

So both end up in the same store. That isn't self-evident: an earlier state of this tutorial had a **Variant B** here, with its own vector database and a search tool in the chat — two separate knowledge stores, one of which could do `#Collection` and citations while the other couldn't. It has been replaced; if you built it, the teardown is at the end of this section under "Migrating away from Variant B."

### Variant A (recommended): let Open WebUI handle the RAG

Open WebUI already comes with the complete RAG pipeline built in — the vector database is included, and Docling is officially supported as an extraction engine.

**1. Start the Docling container:** The Docling server is already included in both compose files in this repo — as the compose *profile* `rag`, so the base setup stays lean:

```bash
# Linux:
docker compose --profile rag up -d

# macOS:
docker compose -f docker-compose.macos.yml --profile rag up -d
```

Docling doesn't need a port mapping: Open WebUI reaches the container directly via the compose network at `http://docling:5001`. (By default the CPU image runs; if you want to use the GPU for faster OCR, set the CUDA variant in the `.env` — see [`.env.example`](.env.example). Note: Docling is RAM-hungry with OCR-heavy PDFs.)

> **Timeouts on large scans:** Open WebUI converts *synchronously* (`POST /v1/convert/file`) and waits without a timeout of its own — so the abort comes from docling-serve, whose `max_sync_wait` defaults to **120 seconds**. In the log it looks like this: `"POST /v1/convert/file HTTP/1.1" 504`. A scanned 190-page magazine with CPU OCR takes more like half an hour to an hour. The compose files therefore set `DOCLING_SERVE_MAX_SYNC_WAIT` to 3600 seconds; adjust it via the `.env` if needed.

**The container's thread count is worth a look.** Docling parallelizes layout detection and OCR through OpenMP, and `OMP_NUM_THREADS` is what tells it how many threads to open. Both compose files feed that from `DOCLING_OMP_THREADS` in the [`.env`](.env.example), default **6**. The value is measured, not guessed — the same scanned 188-page magazine (37.7 MB, no text layer) run five times through the same container:

| `DOCLING_OMP_THREADS` | Duration |
|---|---|
| 2 | 766.4 s |
| 4 | 509.8 s |
| 6 | **346.0 s** |
| 8 | 419.3 s |
| 12 | 656.8 s |

The output was byte-identical in all five runs (815,904 characters) — so this is purely about time, not about quality. And more is decidedly not better: from 8 threads on it goes back uphill, because ONNX Runtime and Torch open thread pools of their own on top and the cores end up oversubscribed. 12 threads are almost twice as slow as 6.

> **If you re-measure, measure on a large document.** The numbers above come from a Mac Studio (M4 Max); on other hardware the optimum sits elsewhere. But be careful with the measurement itself: on an 8-page PDF, the worst of these values happened to be the fastest — on short runs you're measuring model loading, not conversion. A test document that takes at least a few minutes is mandatory.

**2. Configure Open WebUI** under *Admin Settings → Documents*:
- **Content Extraction Engine:** `Docling` with URL `http://docling:5001`
- **Embedding model:** engine `Ollama`, model `bge-m3`, URL `http://ollama:11434` — **on a macOS host, instead use** `http://host.docker.internal:11434` (since Ollama runs natively on the Mac there, not as a container in the compose network)
- **Embedding Batch Size:** `1` → **`64`**
- **Concurrent Requests** (for embedding): `0` → **`4`**

Those last two aren't optional for large documents. With the defaults `batch_size=1` and `concurrent_requests=0` ("unlimited"), Open WebUI sends **every single chunk as its own request — all at once**. A 190-page scan yields roughly 1000 chunks, but Ollama's queue holds only 512 by default (`OLLAMA_MAX_QUEUE`). The import then dies right after a successful extraction with:

```
Ollama embed error (503): server busy, please try again.
maximum pending requests exceeded
```

With `64` and `4` that becomes ~16 batch requests, at most four of them in parallel — gentler *and* faster, since bge-m3 processes a batch almost as quickly as a single text.

> **Note:** Both values are *PersistentConfig* — Open WebUI reads them from the environment only on the very first start and takes them from the database afterwards. An entry in the `.env` or the compose file therefore has no effect; the change has to go through the UI. To inspect what is stored:
>
> ```bash
> docker exec open-webui python3 -c "
> import sqlite3
> db = sqlite3.connect('file:/app/backend/data/webui.db?mode=ro', uri=True)
> for k, v in db.execute(\"select key, value from config where key like 'rag.embedding%'\"):
>     print(k, '=', v)"
> ```

**One more step:** after the `ollama pull`, `bge-m3` also shows up in the chat's model picker — where it has no business being. Select it there by accident and the answer aborts with `"bge-m3:latest" does not support chat`; nothing appears in the backend log, Open WebUI rejects the request outright. So under *Admin Panel → Settings → Models*, turn **visibility off** for `bge-m3`. It remains fully functional as the embedding model — Open WebUI talks to Ollama directly for that and doesn't go through the model list.

**3. Throw in documents:** In Open WebUI, under *Workspace → Knowledge*, create a collection and upload "all the docs lying around." In chat, reference the collection with `#CollectionName` — and the document AI is ready.

**Sources:**
- Open WebUI RAG docs: https://docs.openwebui.com/features/rag
- Docling Serve: https://github.com/docling-project/docling-serve

### Variant C: nightly folder sync with native conversion

If you'd rather just dump files into a folder on the host and leave the rest to the machine, here's the second half. The destination is the same as in Variant A — only the road there is different:

```
/srv/dokumente ──► doc-sync.py ──► Open WebUI API ──► knowledge collection
                   (host, nightly   (/api/v1/files     "Heim-Dokumente"
                    via a timer;     + /knowledge)      — in chat as
                    Docling native)                      #Heim-Dokumente)
```

What comes out at the end is an entirely ordinary knowledge collection: the same one you could have filled by hand. Chunking, embedding and citations are Open WebUI's job here exactly as in Variant A. There is no second knowledge store, and no tool you'd have to switch on in the chat first.

**Why natively instead of in the container?** Because Docker Desktop on Apple Silicon doesn't pass the GPU into containers. Which is why the Docling container's log permanently says:

```
Accelerator device: 'cpu'
```

Natively on the same Mac, Docling does see the hardware and picks the fast path on its own. Measured on the same scanned 188-page magazine:

| Path | Duration | Characters |
|---|---|---|
| Container, 4 threads (the state before this rework) | 509.8 s | 815,904 |
| Container, 6 threads (the optimum, see Variant A) | 346.0 s | 815,904 |
| **Native (MPS + Apple Vision)** | **181.5 s** | 841,999 |

> **The most common misunderstanding at this point:** the thread curve from Variant A applies **to the container only**. Natively, the thread count simply has no effect — 4, 6, 8 and 12 threads produced 180.2 / 180.2 / 181.4 / 180.8 seconds, a spread of 0.7%. The native path depends on MPS and Apple Vision, not on CPU threads. That's why neither the systemd unit nor the launchd plist sets an `OMP_NUM_THREADS`, and putting a 6 in there gains you nothing. `DOCLING_OMP_THREADS` in the `.env` concerns the container from Variant A and nothing else.

**On Linux the gain is smaller.** There, Docker does hand the NVIDIA card into the container: with the CUDA image `docling-serve-cu124` (selectable in the [`.env`](.env.example)), the container computes on the GPU as well. Variant C still makes sense there — for the automatic folder sync — but the head start over Variant A is nowhere near as large as the table above suggests.

**And what Variant C does *not* solve:** it doesn't shorten the wait in the browser. Open WebUI has long since decoupled upload from processing on its own — the upload stores the file and starts a `BackgroundTask`, the file sits at `pending` until it's done, and you may close the tab in peace. So if all you want is to get rid of the hanging progress bar, you don't need Variant C. What C buys you is compute time and a folder that syncs itself — not decoupling. It's worth being honest about that distinction before rebuilding any of this.

**On OCR quality:** Apple Vision and RapidOCR were compared on the same document. Both misread things — umlauts, digits, table cells — just in different places; no systematic advantage of one over the other was discernible. That's also why no OCR engine is hard-wired in [`scripts/docconvert.py`](scripts/docconvert.py): Docling decides for itself (`device='auto'` resolves to `mps`, `ocr_engine=auto` picks `ocrmac`, i.e. Apple Vision). For the same reason there's no platform switch in the code: the same automatic applies on Linux, where it picks CUDA and whichever OCR engine is available there.

**1. Create folders, scripts and the venv** — with its own venv, so the nightly call uses the same environment as the installation. On Linux everything lives under `/srv`, on macOS under `/opt/heim-ki` (on the Mac, `/srv` can't be created because of the sealed system volume):

```bash
# Linux:
sudo mkdir -p /srv/scripts /srv/dokumente
sudo cp scripts/doc-sync.py scripts/docconvert.py scripts/webui_client.py \
        scripts/docscan.py scripts/requirements.txt /srv/scripts/

# System account for the nightly run:
sudo useradd --system --no-create-home --shell /usr/sbin/nologin heim-ki
sudo install -d -o heim-ki -g heim-ki -m 0750 /srv/heim-ki

# /srv/scripts is deliberately owned by root: the timer executes its
# contents, and the login user must not be able to modify what root runs.
sudo chown -R root:root /srv/scripts
sudo chmod -R go-w /srv/scripts

# Build the venv with sudo, so it's also owned by root:
sudo python3 -m venv /srv/scripts/.venv
sudo /srv/scripts/.venv/bin/pip install -r /srv/scripts/requirements.txt

# Documents: the login user writes, the service reads. setgid so new files
# inherit the group; not world-readable.
sudo chown -R "$USER":heim-ki /srv/dokumente
sudo chmod 2750 /srv/dokumente
```

```bash
# macOS (analogous paths, plus a log and backup directory for the launchd jobs;
# everything then belongs to the logged-in user, since the jobs run as
# LaunchAgents in that session — see §3, "Unattended operation". Unlike on
# Linux, there's no privilege boundary here between the login user and the
# service account to protect, since they're the same — so "$USER" is fine
# here, where it would be a mistake on Linux):
sudo mkdir -p /opt/heim-ki/scripts /opt/heim-ki/dokumente /opt/heim-ki/logs /opt/heim-ki/backups
sudo chown -R "$USER" /opt/heim-ki
cp scripts/doc-sync.py scripts/docconvert.py scripts/webui_client.py \
   scripts/docscan.py scripts/requirements.txt /opt/heim-ki/scripts/
python3 -m venv /opt/heim-ki/scripts/.venv
/opt/heim-ki/scripts/.venv/bin/pip install -r /opt/heim-ki/scripts/requirements.txt
```

**All four Python files have to come along.** `doc-sync.py` is only the orchestration; it imports `docscan` (file selection including symlink protection), `docconvert` (the Docling conversion) and `webui_client` (the REST calls). If one of them is missing, the run dies at import time. `requirements.txt` pulls in `docling>=2.0,<3` and `requests>=2.31` — the upper bound on docling is deliberate: a major jump could silently upend the pipeline options in `docconvert.py`, and you'd only notice by way of worse conversions.

**2. Enable API keys globally** — the step without which Variant C never gets off the ground. Open WebUI ships with API keys **switched off**; `open_webui/config.py` has `ENABLE_API_KEYS = os.getenv('ENABLE_API_KEYS', 'False')`. As long as that stands, there is no key to generate in the UI, and `doc-sync.py` has nothing to authenticate with.

The switch sits in the *Admin Settings* under *Authentication* and is called **API Key** ("Allows users to create API keys for programmatic access"). Turn it on and save.

> **Note:** This value is *PersistentConfig* too — Open WebUI reads it from the environment only on the very first start and takes it from the database afterwards (key `auth.enable_api_keys`). An `ENABLE_API_KEYS=true` in the `.env` or the compose file therefore has no effect on an installation that is already running; the change has to go through the UI. To inspect what is stored:
>
> ```bash
> docker exec open-webui python3 -c "
> import sqlite3
> db = sqlite3.connect('file:/app/backend/data/webui.db?mode=ro', uri=True)
> for k, v in db.execute(\"select key, value from config where key like 'auth.%api_key%' or key = 'auth.enable_api_keys'\"):
>     print(k, '=', v)"
> ```
>
> Expected is `auth.enable_api_keys = true`. If it says `false`, the switch hasn't been set yet — and the next step will run into the void.

**3. Create an API key in Open WebUI:** `doc-sync.py` talks to Open WebUI through its REST API and needs a personal key for that. In the UI under *Settings → Account*, section *API keys*, create one and write it into the file the script reads (`WEBUI_API_KEY_FILE`):

```bash
# Linux — the file belongs to the service account and to nobody else:
sudo install -o heim-ki -g heim-ki -m 600 /dev/null /srv/heim-ki/webui-api-key
sudo -u heim-ki tee /srv/heim-ki/webui-api-key >/dev/null <<< 'sk-…'

# macOS:
printf '%s' 'sk-…' > /opt/heim-ki/webui-api-key
chmod 600 /opt/heim-ki/webui-api-key
```

The `chmod 600` isn't decoration: the key sits in plain text on disk and carries the permissions of the account it was created with. Whoever can read it can do everything in Open WebUI that this user can — chats included. (If the section under *Account* is missing entirely, step 2 is still open; on non-admin accounts it is also missing as long as the group doesn't hold the `features.api_keys` permission.)

**4. Create the knowledge collection:** The script looks the collection up **by its name** — `KNOWLEDGE_NAME`, default `Heim-Dokumente`. Either create it beforehand in the UI under *Workspace → Knowledge*, or leave that to the first run with `--create` (step 5).

If the script doesn't find the collection and `--create` is absent, it aborts:

```
FEHLER: Sammlung 'Heim-Dokumente' existiert nicht. Mit --create anlegen — oder KNOWLEDGE_NAME auf Tippfehler prüfen.
```

That is intentional, and the only reason `--create` exists at all. If the script quietly created whatever it couldn't find, a typo in the name — or a `KNOWLEDGE_NAME` that differs between the unit and the plist — would cheerfully produce a second, empty collection on the next run. You'd see nothing of it in the chat: `#Heim-Dokumente` would keep finding the old one while the nightly job diligently fills the new one. An abort with a clear message is the friendlier option.

**5. First run by hand.** Put documents into `/srv/dokumente` or `/opt/heim-ki/dokumente` beforehand.

```bash
# Linux — as the service account, so that manifest and cache get the right
# ownership straight away. The paths for documents, manifest and cache are the
# defaults from doc-sync.py and need no variables; HOME, HF_HOME and
# XDG_CACHE_HOME do: because of "--no-create-home", heim-ki has no $HOME at
# all, and without these three, Docling's model download would either land in
# a directory the account isn't allowed to create, or in the calling user's
# cache — in which case the service would later download everything a second
# time. These are exactly the values from scripts/systemd/doc-sync.service:
sudo -u heim-ki env \
  HOME=/srv/heim-ki/.home \
  HF_HOME=/srv/heim-ki/.cache/huggingface \
  XDG_CACHE_HOME=/srv/heim-ki/.cache \
  /srv/scripts/.venv/bin/python /srv/scripts/doc-sync.py --create

# macOS — the script's defaults are the Linux paths, so set all of them here.
# These exact values also go into the plist later on:
DOCS_DIR=/opt/heim-ki/dokumente \
STATE_FILE=/opt/heim-ki/doc-sync-state.json \
CACHE_DIR=/opt/heim-ki/cache \
LOCK_FILE=/opt/heim-ki/doc-sync.lock \
WEBUI_URL=http://127.0.0.1:3000 \
WEBUI_API_KEY_FILE=/opt/heim-ki/webui-api-key \
KNOWLEDGE_NAME=Heim-Dokumente \
  /opt/heim-ki/scripts/.venv/bin/python /opt/heim-ki/scripts/doc-sync.py --create
```

The very first run additionally downloads Docling's layout and table models from the HuggingFace Hub — that takes noticeably long and happens only once. Which is precisely why the three cache variables are there: they make sure the download lands under `/srv/heim-ki`, i.e. where the service will find it again later. (The full list of environment variables including defaults is in the header of [`scripts/doc-sync.py`](scripts/doc-sync.py); reading it is more reliable than guessing.)

This manual call is deliberately just the initial fill, not a test of the setup: it bypasses the systemd unit and therefore its sandbox, so errors from `ProtectSystem=strict` and relatives won't show up here. The actual test run follows in the next step via `systemctl start`.

What the script does along the way, and why:

- It remembers the SHA-256 of every source file in `STATE_FILE`. Unchanged files are skipped — the expensive step is the conversion, not the upload. (Open WebUI does bring its own diff, but that one compares the checksum of the *uploaded Markdown* — so it answers "has the source file changed?" only after the conversion has already happened, and that is exactly the expensive step.)
- The manifest is written atomically after *every* file (temp file first, then `os.replace`). An abort halfway through therefore costs at most the one file currently in flight, not the whole nightly run.
- Deleted files are removed from the collection, changed ones are replaced.
- The target name contains the full relative path: `steuer/2025.pdf` becomes `steuer_2025.md`. Files with the same name in different subfolders thus don't overwrite each other.
- The finished Markdown is also stored under `CACHE_DIR`, named after the hash of the source. Rebuild the collection and you don't pay for the conversion a second time. **For that, `CACHE_DIR` must not sit inside `DOCS_DIR`** — the conversions are Markdown, and Markdown is what the next scan would read back in as a source file. The script checks this and aborts with a clear message rather than indexing itself.
- A `flock` on `LOCK_FILE` prevents a manual call and the nightly run from writing at the same time.
- A broken file doesn't abort the run; it is logged, and the exit code is non-zero at the end.

**6. Run it nightly:**

*Linux* — as a systemd timer ([`scripts/systemd/`](scripts/systemd/)), 2:00 AM; thanks to `Persistent=true` missed runs are caught up, and the logs go to journald:

```bash
sudo cp scripts/systemd/doc-sync.{service,timer} /etc/systemd/system/
sudo systemctl daemon-reload

# Check the unit before arming it — this reports typos and directives this
# systemd version doesn't know. Please do actually run this step: the unit in
# this repo was written on a macOS machine and could not be checked against a
# real systemd there.
systemd-analyze verify /etc/systemd/system/doc-sync.service

sudo systemctl enable --now doc-sync.timer

# View logs:
journalctl -u doc-sync.service
```

**Test run:** `sudo systemctl start doc-sync.service`, then `journalctl -u doc-sync.service -n 50`. Deliberately through the unit rather than via a direct Python call: only that way do the sandbox directives (`ProtectSystem=strict` etc.) come along, and only that way do errors caused by that very sandbox show up. A `sudo -u heim-ki /srv/scripts/.venv/bin/python …` bypasses the unit entirely and would never see them.

> **Why the unit doesn't set `PrivateDevices=yes`.** Its predecessor did. The directive hides `/dev/nvidia*`, `torch.cuda.is_available()` then returns `False`, and Docling computes layout and OCR on the CPU — which is precisely the state this rework is meant to abolish. The line is therefore absent on purpose, and the `.service` file says so in a comment. On a host without a GPU, or if you weigh the hardening higher than the runtime, you can add it back and accept a markedly longer nightly run.

On the very first run, Docling downloads its models from HuggingFace. The service runs as `heim-ki` (`--no-create-home`) and therefore has no `$HOME` at all, and `ProtectHome=yes` hides `/home` anyway — so the unit actively redirects `HOME`, `HF_HOME` and `XDG_CACHE_HOME` under `/srv/heim-ki`. That directory has to exist and be owned by `heim-ki` (done above with `install -d -o heim-ki -g heim-ki`), otherwise the unit won't start. Known limitation: should a future docling version instead want to write package-relatively into the venv, that would still fail under `ProtectSystem=strict` — check this on the first run with whichever version is actually installed.

*macOS* — as a LaunchAgent ([`scripts/launchd/de.heim-ki.doc-sync.plist`](scripts/launchd/de.heim-ki.doc-sync.plist)); the `/opt/heim-ki` paths are already in the plist as `EnvironmentVariables`:

```bash
mkdir -p ~/Library/LaunchAgents
cp scripts/launchd/de.heim-ki.doc-sync.plist ~/Library/LaunchAgents/
launchctl load -w ~/Library/LaunchAgents/de.heim-ki.doc-sync.plist

# View logs:
tail -f /opt/heim-ki/logs/doc-sync.log
```

Deliberately a **LaunchAgent in the user session**, not a root daemon: at 2:00 AM the sync needs Open WebUI in the container (Docker Desktop/OrbStack only run in a logged-in session) — and it needs the GPU, which a session-less daemon doesn't get. The latter weighs particularly heavily here: without MPS the entire reason for Variant C is gone, and the only symptom is the runtime. So set up §3, "Unattended operation" (automatic login, "Start at login," `pmset`), otherwise the nightly job runs into thin air.

(launchd catches up on a missed run if the Mac was merely asleep at the scheduled time — but not after a full shutdown or without a logged-in session.)

**7. Use it:** In chat, reference the collection with `#Heim-Dokumente` and ask away ("What does my lease say about the notice period?"). The answer comes with source citations — the documents sit in a perfectly ordinary knowledge collection, and Open WebUI can't tell whether they arrived through the browser or through the nightly job.

> **Note:** Variant C does *not* use the Docling container from Variant A, but the Docling Python library directly on the host — so it doesn't need the compose profile `rag`. Both variants can still run side by side: they write into the same store. You can mix them in one collection, or give the nightly job its own via `KNOWLEDGE_NAME`.

**Sources:**
- Docling docs: https://docling-project.github.io/docling/
- Open WebUI RAG docs: https://docs.openwebui.com/features/rag
- Ollama embeddings: https://docs.ollama.com/api

### Migrating away from Variant B

If you built the earlier state of this tutorial — own indexer, own ChromaDB, search tool in the chat — here's how to clean up. **Set up Variant C first and let it run through successfully once**; after that the old index is expendable.

```bash
# Linux:
sudo systemctl disable --now rag-indexer.timer
sudo rm -f /etc/systemd/system/rag-indexer.{service,timer}
sudo systemctl daemon-reload

# macOS:
launchctl unload -w ~/Library/LaunchAgents/de.heim-ki.rag-indexer.plist
rm -f ~/Library/LaunchAgents/de.heim-ki.rag-indexer.plist

# Both: the Chroma container is gone from the compose files, but its volume
# stays behind. It holds the old RAG index and isn't needed any more —
# deleting it is a deliberate decision:
docker rm -f chroma
docker volume rm chroma-data
```

Plus four small things that would otherwise quietly linger:

- **The tool in the chat:** in Open WebUI, under *Workspace → Tools*, delete the tool "Heim-Dokumente durchsuchen." Otherwise it keeps pointing at a database that no longer exists — and the model will still call it as long as it's enabled on the model. The template `tools/heim_docs_suche.py` has been removed from the repo.
- **Tidy up the `.env`:** `CHROMA_IMAGE` and `CHROMA_HOST_PORT` have become inert and can go; likewise any `CHROMA_URL` in your own unit or plist.
- **The old manifest:** `rag-index-state.json` is read by nobody any more. `doc-sync.py` keeps its own (`doc-sync-state.json`) and starts from zero — which is why the first run converts the entire stock once more. Afterwards the old file can go — depending on how old the installation is, it sits at `/srv/rag-index-state.json` or `/srv/heim-ki/rag-index-state.json` (on macOS analogously in `/opt/heim-ki/`):
  ```bash
  sudo rm -f /srv/rag-index-state.json /srv/heim-ki/rag-index-state.json
  ```
- **Backups:** [`scripts/backup.sh`](scripts/backup.sh) now saves the manifest as `doc-sync-state-*.json` instead of `rag-index-state-*.json`. The automatic cleanup via `KEEP_DAYS` only knows the new name — so the old `rag-index-state-*.json` files in the backup directory stay put instead of disappearing after 14 days. No new ones are added; if you want the existing ones gone, delete them by hand.

- Everyone in the household reaches a ChatGPT-like interface at **`http://chat.heim.lan`** — no ports, no IP addresses.
- The AI knows your own documents (RAG with Docling + bge-m3 + Open WebUI) — via upload in the browser, and optionally as a nightly folder sync on top.

### Acceptance: did the hardening actually take effect?

The protections from §5–§7 have an unpleasant property: if they *don't* take effect, you won't notice in day-to-day use. The interface works, the models answer — the unauthenticated Ollama API is just still sitting open on the network. Walk through these eight checks once after setup; they need the real host and can't be ticked off in advance.

```bash
# 1. Is the NGINX configuration syntactically sound?
sudo nginx -t

# 2. Rejected without credentials? Expected: 401
curl -si http://ollama.heim.lan/api/tags | head -1

# 3. Allowed through with credentials? Expected: 200
curl -si -u heim-ki:PASSWORD http://ollama.heim.lan/api/tags | head -1

# 4. From a device OUTSIDE the <LAN-CIDR>. Expected: 403
curl -si -u heim-ki:PASSWORD http://ollama.heim.lan/api/tags | head -1

# 5. Is Ollama really listening on loopback only? Expected: only 127.0.0.1,
#    nowhere 0.0.0.0 or a LAN address
sudo ss -ltnp | grep 11434          # Docker host
lsof -iTCP:11434 -sTCP:LISTEN       # on the Mac workstation

# 6. Is the tunnel up, and on which addresses? Expected: 127.0.0.1:11435
#    for NGINX and the docker0 gateway address for Open WebUI
sudo ss -ltn | grep 11435
ip -4 addr show docker0             # does the gateway address match §5?

# 7. Does Open WebUI reach the workstation? Expected: model list
docker exec open-webui curl -sS http://host.docker.internal:11435/api/tags

# 8. Does the document sync run through under the full sandbox? (Variant C only)
systemd-analyze verify /etc/systemd/system/doc-sync.service
sudo systemctl start doc-sync.service
journalctl -u doc-sync.service -n 50
```

On checks 3 and 4: `401` means "credentials missing", `403` means "source IP not in the allowlist". Both answers are good news — they prove `satisfy all` is working. If check 2 returns a model list instead, the `auth_basic` configuration is ineffective; if it returns `500`, the htpasswd file is missing or the path in `auth_basic_user_file` is wrong (`nginx -t` won't catch that, because the file is only opened at runtime).

On check 8: The first run downloads the Docling models and takes correspondingly long. It is the actual test of the sandbox — calling it directly via `sudo -u heim-ki …` bypasses the unit and would not surface write errors that only `ProtectSystem=strict` causes. The `systemd-analyze verify` in front of it is part of the acceptance here as well, not mere decoration: the unit in this repo was written on a macOS machine and has never run against a real systemd.

#    https://github.com/open-webui/open-webui/releases

## 10. HTTPS on the LAN

HTTPS on the LAN is more than cosmetic: without a secure context, browsers block **microphone access** — Open WebUI's voice input/output simply doesn't work over `http://` from other devices. It also gets rid of the "Not secure" warnings in the address bar, which in a family setting only raise questions.

The approach uses [mkcert](https://github.com/FiloSottile/mkcert): a small private certificate authority (CA) on the Docker host that issues certificates for the three `.lan` names.

**Step 1 — create the CA and issue a certificate** (on the Docker host):

```bash
sudo apt install mkcert libnss3-tools    # Linux
brew install mkcert nss                  # macOS ("nss" only needed for Firefox)

mkcert -install        # creates the local CA and registers it on THIS machine

# One certificate for all three names:
mkcert chat.heim.lan ollama.heim.lan ollama-ws.heim.lan

# On a macOS host that should also be reachable via Bonjour (§6, option 4),
# include the .local name — otherwise the browser complains about the
# certificate when you go through .local:
#   mkcert chat.heim.lan ollama.heim.lan ollama-ws.heim.lan heim-ki.local
# Note: the file names below are then "chat.heim.lan+3.pem" instead of "+2".

# Linux:
sudo mkdir -p /etc/nginx/certs
sudo cp chat.heim.lan+2.pem     /etc/nginx/certs/heim-ki.pem
sudo cp chat.heim.lan+2-key.pem /etc/nginx/certs/heim-ki-key.pem

# macOS (Homebrew NGINX):
sudo mkdir -p /opt/homebrew/etc/nginx/certs
sudo cp chat.heim.lan+2.pem     /opt/homebrew/etc/nginx/certs/heim-ki.pem
sudo cp chat.heim.lan+2-key.pem /opt/homebrew/etc/nginx/certs/heim-ki-key.pem
```

**Step 2 — switch NGINX to HTTPS:** The finished configuration is at [`nginx/heim-ki-https.conf`](nginx/heim-ki-https.conf) — it redirects port 80 to 443 and **replaces** the HTTP variant:

```bash
# Linux (Debian/Ubuntu):
sudo cp nginx/heim-ki-https.conf /etc/nginx/sites-available/
sudo rm -f /etc/nginx/sites-enabled/heim-ki.conf
sudo ln -s /etc/nginx/sites-available/heim-ki-https.conf /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx

# macOS (Homebrew): adjust the certificate path in the file to /opt/homebrew/etc/nginx/certs,
# then:
sudo rm -f /opt/homebrew/etc/nginx/servers/heim-ki.conf
sudo cp nginx/heim-ki-https.conf /opt/homebrew/etc/nginx/servers/
sudo nginx -t && sudo brew services restart nginx
```

**Step 3 — install the CA on family devices.** This is the price of LAN HTTPS: every device has to trust your own CA once. The CA file is at `$(mkcert -CAROOT)/rootCA.pem` — **only distribute `rootCA.pem`, never `rootCA-key.pem`!**

- **Windows:** double-click `rootCA.pem` → *Install Certificate* → store location *Trusted Root Certification Authorities*.
- **Android:** copy the file to the device → *Settings → Security → Install a certificate (CA certificate)*.
- **iOS/iPadOS:** open `rootCA.pem` e.g. via AirDrop/Mail → install profile → additionally enable it under *Settings → General → About → Certificate Trust Settings*.
- **macOS/Linux:** import into the keychain or system trust store; Firefox manages its own store (*Settings → Certificates → Import*).

**Alternative:** If you'd rather use [Caddy](https://caddyserver.com) as a container instead of the host NGINX, `tls internal` gets you the same thing automatically (Caddy brings its own CA) — distributing the CA file to devices is still necessary there too.

## 11. Backup & Restore

What needs to be backed up is anything that can't be recreated: the **Open WebUI volume** (users, chats, knowledge collections — and with them the vectors) and the **document sync manifest** (`doc-sync-state.json`, Variant C only). The Ollama models are deliberately excluded — `ollama pull` can always fetch them again, and the Markdown cache under `CACHE_DIR` isn't worth a backup either: it can be regenerated at any time, just not for free.

The script [`scripts/backup.sh`](scripts/backup.sh) does exactly that (including cleaning up old backups, default: 14 days) and runs daily at 3:30 AM — that is, after the nightly document sync. To tar up the volumes it starts a small Alpine container; the image is pinned to a fixed digest via `ALPINE_IMAGE` (overridable via environment variable), so a fresh, unvetted `:latest` image isn't pulled on every run.

*Linux* — via a systemd timer:

```bash
sudo mkdir -p /srv/scripts    # already exists if §7 Variant C was set up
sudo cp scripts/backup.sh /srv/scripts/
sudo chown root:root /srv/scripts/backup.sh
sudo chmod 755 /srv/scripts/backup.sh
sudo cp scripts/systemd/heim-ki-backup.{service,timer} /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now heim-ki-backup.timer

# Run manually / view logs:
sudo systemctl start heim-ki-backup.service
journalctl -u heim-ki-backup.service
```

The backup deliberately stays root, because it needs the Docker socket — the docker group would be root-equivalent anyway, so it wouldn't be a real gain. The actual protection is that `/srv/scripts` is owned by root (§7): the login user can't modify `backup.sh`, even though the script itself runs with root privileges.

*macOS* — via a launchd job ([`scripts/launchd/de.heim-ki.backup.plist`](scripts/launchd/de.heim-ki.backup.plist), target `/opt/heim-ki/backups`). This job also runs as a **LaunchAgent in the user session**, because the docker CLI can only reach the Docker Desktop/OrbStack daemon there (the socket is at `~/.docker/run/docker.sock`, not `/var/run/docker.sock`). If Docker isn't reachable at night, `backup.sh` aborts with an error instead of silently writing an empty backup — so for reliable nightly runs, set up §3, "Unattended operation":

```bash
# Directories already exist if §7 Variant C was set up — otherwise:
sudo mkdir -p /opt/heim-ki/scripts /opt/heim-ki/logs /opt/heim-ki/backups
sudo chown -R "$USER" /opt/heim-ki

cp scripts/backup.sh /opt/heim-ki/scripts/ && chmod +x /opt/heim-ki/scripts/backup.sh
mkdir -p ~/Library/LaunchAgents
cp scripts/launchd/de.heim-ki.backup.plist ~/Library/LaunchAgents/
launchctl load -w ~/Library/LaunchAgents/de.heim-ki.backup.plist

# Run manually / view logs:
launchctl start de.heim-ki.backup
tail -f /opt/heim-ki/logs/backup.log
```

The target directory is `/srv/backups/heim-ki` or `/opt/heim-ki/backups` (changeable via `BACKUP_DIR` — ideally a NAS mount, so the backup doesn't live on the same disk as the data).

**Restore** (macOS: `docker compose` each with `-f docker-compose.macos.yml` and the backup path `/opt/heim-ki/backups`):

```bash
docker compose down
docker run --rm -v open-webui-data:/data -v /srv/backups/heim-ki:/backup alpine \
  sh -c "rm -rf /data/* && tar xzf /backup/open-webui-data-YYYY-MM-DD.tar.gz -C /data"
docker compose up -d
```

## 12. Wake-on-LAN for the workstation

So the workstation with the big GPU doesn't have to run continuously, you can wake it on demand from the LAN:

**One-time setup on a Windows workstation:**
1. Enable "Wake on LAN" (or similar) in the **BIOS/UEFI**.
2. In Windows, in **Device Manager**, under the network adapter's *Power Management*, enable "Allow this device to wake the computer" and under *Advanced*, enable "Wake on Magic Packet."
3. **Disable Windows Fast Startup** (*Power Options → Choose what the power buttons do*) — with Fast Startup active, "Shut down" is a hybrid state from which WoL often doesn't work.
4. Note the **MAC address**: `ipconfig /all` → "Physical Address."

**For a Mac as a workstation:** In *System Settings → Energy* (or *Battery → Options*), enable "**Wake for network access**" — this wakes the Mac from **sleep** (not from a powered-off state; Macs don't support WoL from shutdown). Works reliably over Ethernet; with Wi-Fi-only operation it's a matter of luck. MAC address: *System Settings → Network → Details*.

**Waking from the Docker host** with [`scripts/wol.sh`](scripts/wol.sh):

```bash
sudo apt install wakeonlan     # Linux
brew install wakeonlan         # macOS host

./scripts/wol.sh AA:BB:CC:DD:EE:FF
```

A minute later, the workstation's Ollama is available at `ollama-ws.heim.lan` (the native app starts automatically with Windows; on the Mac the LaunchAgent from §5 takes care of it). **Tip:** A Fritz!Box can also do this without a script — in the device details under *Home Network → Network* there's a "Start computer" button.

## 13. Troubleshooting

If you suspect one of the protections from §5–§7 isn't taking effect, work through the acceptance checklist in §8 first — it usually narrows down the cause faster than the table below.

| Symptom | Cause & fix |
|---|---|
| Containers don't see the GPU | Test: `docker run --rm --gpus all nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi`. If that fails: `sudo nvidia-ctk runtime configure --runtime=docker && sudo systemctl restart docker`. After a driver update: restart the host. |
| Responses suddenly very slow | `docker exec ollama ollama ps` shows whether the model is (partially) running on the CPU (`XX%/YY% CPU/GPU`). Fix: a smaller/more heavily quantized model, or the §4 tips (`OLLAMA_MAX_LOADED_MODELS=1`). |
| First prompt "hangs" | The model is currently being loaded into VRAM — this takes a while for larger models. `OLLAMA_KEEP_ALIVE` (§4) prevents frequent reloading. |
| `nginx: [emerg] invalid parameter "<LAN-CIDR>"` | The copied configuration still contains the placeholder (§6). Replace it with your own network, e.g. `192.168.2.0/24` — while the test fails, NGINX loads none of the file, so `chat.heim.lan` stays dead too. |
| `403 Forbidden` from `ollama.heim.lan` | Since the security hardening, usually the IP allowlist (`allow <LAN-CIDR>; deny all;` in §6) — access from outside the allowed network is rejected with 403; check which IP the client is coming from. Only after ruling that out does Ollama's own Host header protection come into play — the §6 configuration therefore sends `Host 127.0.0.1:11434`; check whether the repo's configuration is really active (`nginx -T \| grep -A5 ollama`). |
| `401 Unauthorized` from `ollama.heim.lan` | Missing or wrong basic-auth credentials — since the hardening, the Ollama vHosts require `auth_basic` (§6) in addition to the IP allowlist; check or reset the credentials in the password file (`sudo htpasswd /etc/nginx/heim-ki.htpasswd heim-ki`). |
| Upload fails with `413 Request Entity Too Large` | `client_max_body_size` missing/too small — included in `nginx/heim-ki.conf` (100 MB), reload NGINX. |
| Docling container crashes / host swaps on large PDFs | Docling OCR is RAM-hungry. Split large scans, or give the service a `mem_limit` in the compose file; if needed, upload documents one at a time. |
| `ollama-ws.heim.lan` dead after a Windows restart (WSL path) | The WSL IP has changed — reset the port proxy, or switch to *mirrored networking* or the native app (§5). |
| Chat replies `"bge-m3:latest" does not support chat` | The embedding model is selected as the chat model. Pick a real chat model in the composer and resend; to prevent a repeat, hide `bge-m3` under *Admin Panel → Settings → Models* (§7 Variant A). |
| Upload aborts with `Ollama embed error (503): ... maximum pending requests exceeded` | Extraction succeeded; embedding overruns Ollama's queue. In *Admin Settings → Documents* set **Embedding Batch Size** to 64 and **Concurrent Requests** to 4 (§7 Variant A) — not via the `.env`, these values come from the database. |
| Upload aborts, `"POST /v1/convert/file" 504` in `docker logs docling` | The conversion exceeds docling-serve's `max_sync_wait` (image default 120 s). Raise `DOCLING_SERVE_MAX_SYNC_WAIT` in the `.env` (§7 Variant A). If it aborts *immediately* and the result is empty, the PDF itself is more likely broken — check with `python3 -c "from pypdf import PdfReader; print(len(PdfReader('file.pdf').pages))"`; "Stream has ended unexpectedly" means it was downloaded incompletely. |
| `port is already allocated` on startup | Another service holds the host port. Which one? `lsof -nP -iTCP:<port> -sTCP:LISTEN`, plus `docker ps --format '{{.Names}}\t{{.Ports}}'`. Note that a container on `0.0.0.0:<port>` also blocks a `127.0.0.1:<port>` binding. |
| Doc sync aborts: `Sammlung '…' existiert nicht` | An intentional abort, not a bug in the script (§7 Variant C): the collection is looked up **by name** via `KNOWLEDGE_NAME`. First check the name against *Workspace → Knowledge* — capitalization and hyphens count. If it really is new, run once with `--create`. |
| Doc sync runs, but the chat finds nothing | Are the files landing in the collection the chat actually references? (`#Heim-Dokumente` pulls in the collection with *that* name — with two similarly named ones it's easy to grab the wrong one.) Logs: Linux `journalctl -u doc-sync.service`, macOS `/opt/heim-ki/logs/doc-sync.log`. |
| Doc sync is far slower at night than by hand | Points to missing GPU access. Linux: is `PrivateDevices=yes` in the unit? (It does *not* belong there, §7 Variant C.) macOS: the LaunchAgent needs a logged-in session, otherwise there's no MPS. Search the log for `Accelerator device:` — if it says `'cpu'`, that's exactly the cause. |
| macOS: Ollama painfully slow, Mac fan spinning | Is Ollama accidentally running as a container? On macOS, containers have **no GPU access** — Ollama must run natively (`brew services start ollama`, §3) and Open WebUI must point to `host.docker.internal:11434` via `docker-compose.macos.yml`. |
| macOS: Open WebUI can't reach Ollama | Is native Ollama running? (`ollama ps`, `brew services list`). The Open WebUI *Connections* must contain `http://host.docker.internal:11434`, not `http://ollama:11434` — there's no Ollama service name in the macOS compose file. |
| macOS: nightly jobs (doc sync/backup) didn't run | The jobs run as LaunchAgents only in a **logged-in session** with Docker Desktop/OrbStack running and the Mac awake — see §3, "Unattended operation" (auto-login, "Start at login," `pmset`). Status: `launchctl list \| grep heim-ki`; logs: `/opt/heim-ki/logs/*.log`. |
| General diagnostics | `docker compose ps` (health checks!; macOS: with `-f docker-compose.macos.yml`, the Docling service additionally with `--profile rag` — or simply `docker ps`), `docker logs open-webui`, `docker stats`; Linux only: `docker logs ollama`, `nvidia-smi` (macOS: Ollama native → `ollama ps`, logs via `brew services`). |

## 14. Further ideas

- **Model recommendations for 4 GB VRAM:** `llama3.2:3b`, `qwen2.5:3b`, `phi3:mini` — all in the [Ollama Library](https://ollama.com/library).
