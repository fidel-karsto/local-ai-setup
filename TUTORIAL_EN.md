# Local Home AI with Open WebUI, Ollama & RAG — completely cloud-free

**Tutorial: A private AI assistant on your own LAN that can also search your own documents**

> Based on a setup by Matthias Kallenbach (LinkedIn post). Goal: a ChatGPT-like interface for everyone in the household ("Mom can use the home AI too"), where **no data ever leaves your own network**.

**Besides the tutorial, this repo contains the finished configuration files:**
[`docker-compose.yml`](docker-compose.yml) (Linux) · [`docker-compose.macos.yml`](docker-compose.macos.yml) (macOS) · [`.env.example`](.env.example) · [`nginx/`](nginx) (HTTP and HTTPS configuration) · [`scripts/`](scripts) (RAG indexer, backup, Wake-on-LAN, systemd and launchd units) · [`tools/heim_docs_suche.py`](tools/heim_docs_suche.py) (Open WebUI tool)

The Docker host can be a **Linux machine with an NVIDIA GPU** or an **Apple Silicon Mac** — wherever the paths diverge, it's noted in the relevant section.

## 1. What are we building? (Architecture overview)

The setup consists of two machines and several services:

```
                        ┌─────────────────────────────────────┐
                        │  Docker host (Linux or macOS, 24/7) │
                        │  GPU: NVIDIA (CUDA) or Apple Silicon│
  LAN clients           │                                     │
  (browser, phone,      │  ┌───────────┐   ┌───────────────┐  │
   "Mom") ──────────►   │  │  NGINX    │──►│  Open WebUI   │  │
                        │  │  Reverse  │   └───────┬───────┘  │
  chat.heim.lan         │  │  Proxy    │           │          │
  ollama.heim.lan       │  │  (Port    │   ┌───────▼───────┐  │
  ollama-ws.heim.lan    │  │  80/443)  │──►│ Ollama        │  │
                        │  └─────┬─────┘   │ (Container,   │  │
                        │        │         │  GPU access)  │  │
                        │        │         │  + bge-m3     │  │
                        │        │         └───────────────┘  │
                        │        │         ┌───────────────┐  │
                        │        │         │ RAG pipeline: │  │
                        │        │         │ Docling +     │  │
                        │        │         │ ChromaDB +    │  │
                        │        │         │ bge-m3        │  │
                        │        │         │ (nightly      │  │
                        │        │         │  batch job)   │  │
                        │        │         └───────────────┘  │
                        │        │                            │
                        └────────┼────────────────────────────┘
                                 │
                        ┌────────▼────────────────────────────┐
                        │  Workstation (Windows or macOS)      │
                        │  Ollama "on demand" — only on        │
                        │  while the machine is running; for   │
                        │  larger models with a stronger GPU   │
                        └─────────────────────────────────────┘
```

**The components in detail:**

| Component | Role |
|---|---|
| **[Ollama](https://ollama.com)** | Local LLM server. Runs on the Docker host (Linux: as a container with a CUDA GPU; macOS: natively with Metal, see §3) **and** additionally "on demand" on the workstation (Windows or macOS). |
| **[Open WebUI](https://github.com/open-webui/open-webui)** | ChatGPT-like web interface for Ollama — with user management, document upload, and built-in RAG. |
| **[bge-m3](https://ollama.com/library/bge-m3)** | Multilingual embedding model (BAAI). Converts text into vectors — the foundation for document search (RAG). Very well suited for German (and other non-English languages). |
| **[Docling](https://github.com/docling-project/docling)** | Open-source tool from IBM Research: converts PDF, DOCX, PPTX, HTML, etc. into clean, structured Markdown/JSON — including tables and layout recognition. (Written as "Dockling" in the original post — Docling is meant.) |
| **[ChromaDB](https://www.trychroma.com)** | Vector database. Stores the embeddings generated by bge-m3 and returns the matching document snippets for a given question. |
| **[NGINX](https://nginx.org)** | Reverse proxy on the Docker host. Turns `http://192.168.x.y:11434` into nice, meaningful names like `http://ollama.heim.lan` — "no weird ports." |

**RAG** (Retrieval-Augmented Generation) means: before the language model answers, the system searches your own documents for relevant passages and feeds them to the model as context. This lets the home AI answer questions about your own PDFs, contracts, manuals, etc.

## 2. Prerequisites

**Hardware** (one of the two host variants):
- **Linux host:** A machine that runs continuously (mini PC, old desktop, home server), with an NVIDIA GPU with at least 4 GB VRAM. That's enough for small models (e.g. 3B–7B quantized) and embeddings. **But:** 4 GB is tight when the chat model and embedding model are needed at the same time — and that's exactly what happens with RAG. See "Realistic expectations with 4 GB VRAM" in §4.
- **macOS host:** An Apple Silicon Mac (e.g. a Mac mini) with at least 16 GB RAM. Thanks to unified memory, a large portion of RAM is available to the model as "VRAM" — a 16 GB Mac often handles RAG more comfortably than a 4 GB NVIDIA card. **Important:** Docker containers have no GPU access on macOS, so Ollama runs *natively* on the Mac (§3/§4).
- Optional: a workstation (Windows or Mac) with more GPU power for larger models "on demand."

**Software:**
- Docker + Docker Compose on the host → Linux: [Docker Engine](https://docs.docker.com/engine/install/); macOS: [Docker Desktop](https://docs.docker.com/desktop/setup/install/mac-install/) or [OrbStack](https://orbstack.dev)
- Linux host only: NVIDIA drivers + **NVIDIA Container Toolkit** (so containers can use the GPU) → [installation guide](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/install-guide.html)
- macOS host only: [Homebrew](https://brew.sh) for Ollama, NGINX, etc.
- On the workstation: nothing special — Ollama is available natively for Windows and macOS. (WSL2 only for the advanced path in §5 → [Microsoft docs](https://learn.microsoft.com/en-us/windows/wsl/install))

**Network:**
- The ability to assign local DNS names — realistically via **Pi-hole/AdGuard Home**, or as a fallback via a `hosts` file on the clients. A Fritz!Box alone *cannot* do this freely (details and options in §6, step 1).

## 3. Preparing the Docker host (GPU access)

### Linux (NVIDIA)

Install the NVIDIA Container Toolkit (Ubuntu/Debian, abridged — details at the link above):

```bash
curl -fsSL https://nvidia.github.io/libnvidia-container/gpgkey | \
  sudo gpg --dearmor -o /usr/share/keyrings/nvidia-container-toolkit-keyring.gpg
curl -s -L https://nvidia.github.io/libnvidia-container/stable/deb/nvidia-container-toolkit.list | \
  sed 's#deb https://#deb [signed-by=/usr/share/keyrings/nvidia-container-toolkit-keyring.gpg] https://#g' | \
  sudo tee /etc/apt/sources.list.d/nvidia-container-toolkit.list

sudo apt-get update && sudo apt-get install -y nvidia-container-toolkit
sudo nvidia-ctk runtime configure --runtime=docker
sudo systemctl restart docker
```

Test:

```bash
docker run --rm --gpus all nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi
```

If `nvidia-smi` shows the GPU, everything is ready.

### macOS (Apple Silicon)

On the Mac, the whole toolkit part is skipped — but a different basic rule applies: **Docker containers have no GPU access on macOS** (Docker runs there in a VM without Metal passthrough). Running Ollama in a container on a Mac would therefore be pure CPU torture. That's why only **Ollama natively** is installed on the macOS host (it uses the GPU via Metal automatically, with zero configuration), and everything else runs in containers:

```bash
brew install ollama
brew services start ollama    # starts Ollama as a service at every login
```

Install and start Docker Desktop (or OrbStack) — no further preparation is needed. The test here is simple:

```bash
ollama run llama3.2:3b "Say hello"    # responds promptly? Metal is working.
```

> ⚠️ **Unattended operation (24/7 host, e.g. headless Mac mini):** Unlike systemd services on Linux, on the Mac *all* the building blocks depend on a logged-in user session: `brew services start ollama` (without sudo) creates a LaunchAgent that starts on **login** — not on boot — and Docker Desktop/OrbStack likewise only run within a session. After a restart (power outage, update) without a login, the home AI is dead. So set this up once:
>
> 1. Enable **automatic login**: *System Settings → Users & Groups → Automatic login* (not possible with FileVault enabled).
> 2. Let **Docker Desktop/OrbStack start at login** (the "Start at login" setting).
> 3. **Disable sleep** — a sleeping Mac doesn't answer requests and doesn't run nightly jobs: `sudo pmset -a sleep 0 disksleep 0`. Also useful: `sudo pmset -a autorestart 1` (automatic restart after a power outage).
>
> The nightly jobs from §7/§11 also run as LaunchAgents in the user session for exactly this reason, not as root daemons.

## 4. Ollama + Open WebUI as containers

### Linux host

The finished [`docker-compose.yml`](docker-compose.yml) is in this repo; it's configured via an `.env`:

```bash
git clone https://github.com/fidel-karsto/local-ai-setup.git && cd local-ai-setup
cp .env.example .env      # adjust if needed (image versions, timezone, …)
docker compose up -d
```

The key points of the compose file (abridged — the file in the repo is the source of truth):

```yaml
services:
  ollama:
    image: ollama/ollama:0.33.1          # pinned instead of :latest — see "Updates" (§9)
    environment:
      - OLLAMA_KEEP_ALIVE=30m            # don't unload models from VRAM immediately
      - OLLAMA_MAX_LOADED_MODELS=1       # with 4 GB VRAM: only 1 model at a time
    volumes:
      - ollama-data:/root/.ollama
    ports:
      - "127.0.0.1:11434:11434"          # localhost only — NGINX (§6) is the LAN entry point
    deploy: …                            # GPU reservation, see file

  open-webui:
    image: ghcr.io/open-webui/open-webui:v0.11.1
    environment:
      - OLLAMA_BASE_URL=http://ollama:11434
    volumes:
      - open-webui-data:/app/backend/data
    ports:
      - "127.0.0.1:3000:8080"            # localhost only, see above
```

Both ports are deliberately **bound to `127.0.0.1` only**: from the LAN, access happens exclusively through the NGINX from §6 — so there's exactly one entry point. Ollama itself has no authentication whatsoever, so its vHost there sits behind an IP allowlist **and** basic auth (`satisfy all`); without both, there is no access to `/api/pull`, `/api/delete` and friends. (This also means `http://<docker-host-ip>:3000` will *not* work from other machines — set up §6 first and use `http://chat.heim.lan`, or for testing use an SSH tunnel: `ssh -L 3000:localhost:3000 <docker-host>`.)

Pull models:

```bash
# A small chat model that fits in 4 GB VRAM:
docker exec ollama ollama pull llama3.2:3b

# The embedding model for RAG:
docker exec ollama ollama pull bge-m3
```

**First login & registration:** On first launch, create an admin account. Then close open self-registration — otherwise anyone on the LAN can create an account: set `ENABLE_SIGNUP=false` in the `.env` and run `docker compose up -d` again (or in the *Admin Settings* set the default role for new users to "Pending" and approve family members individually).

**Realistic expectations with 4 GB VRAM:** `llama3.2:3b` (~2 GB) and `bge-m3` (~1.2 GB) each fit comfortably into VRAM individually — but with RAG, both are needed in quick succession (first the embedding of the question, then the answer from the chat model). With `OLLAMA_MAX_LOADED_MODELS=1`, the models take turns (short loading pauses per request); without that limit, some layers end up on the CPU (it works, but noticeably slower). `OLLAMA_KEEP_ALIVE=30m` at least prevents models from being unloaded again after just 5 minutes of idle time. Anyone who uses RAG regularly benefits significantly from more VRAM — or should deliberately compute embeddings on the CPU.

### macOS host

On the Mac, Ollama already runs natively (§3) — only the rest goes into containers. For this there's a dedicated compose file, [`docker-compose.macos.yml`](docker-compose.macos.yml): it contains no Ollama service and instead points to the Mac's native Ollama via `OLLAMA_BASE_URL=http://host.docker.internal:11434`:

```bash
git clone https://github.com/fidel-karsto/local-ai-setup.git && cd local-ai-setup
cp .env.example .env
docker compose -f docker-compose.macos.yml up -d

# Pull models directly, natively (no "docker exec" needed):
ollama pull llama3.2:3b
ollama pull bge-m3
```

The notes above on **first login & registration** apply unchanged. Instead of the VRAM gymnastics, the unified-memory rule of thumb applies on the Mac: macOS grants models roughly up to ~⅔ of RAM — on a 16 GB Mac, `llama3.2:3b` and `bge-m3` run comfortably side by side, and even 7B–8B models are feasible. If you want to set `OLLAMA_KEEP_ALIVE` or similar: `launchctl setenv OLLAMA_KEEP_ALIVE 30m` (followed by `brew services restart ollama`) takes effect immediately, but silently disappears again after a restart — for permanently wiring such variables, use a dedicated LaunchAgent instead of `brew services` — the bundled [`scripts/launchd/de.heim-ki.ollama-ws.plist`](scripts/launchd/de.heim-ki.ollama-ws.plist), however, no longer works as a template for this: it's now hardwired to the workstation role from §5 (`OLLAMA_HOST` fixed there to `127.0.0.1:11434`, for the SSH tunnel). For the Docker host, a simple copy of your own with a different `Label` and `OLLAMA_KEEP_ALIVE` in `EnvironmentVariables` is enough. And because Ollama natively listens only on `127.0.0.1` by default, the same security logic applies as on Linux: the NGINX from §6 is the only entry point from the LAN.

**Sources:**
- Ollama Docker image: https://hub.docker.com/r/ollama/ollama
- Open WebUI docs: https://docs.openwebui.com

## 5. Ollama "on demand" on the workstation (Windows or macOS)

The workstation typically has more GPU power, but doesn't run around the clock. That's why a second Ollama server runs there, available only when the machine is on.

### Windows: native app (recommended)

Install [Ollama for Windows](https://ollama.com/download/windows), then set `OLLAMA_HOST=0.0.0.0` as a *user environment variable* (`Control Panel → Environment Variables`) and restart Ollama so it's reachable from the LAN. Finally, open the port in the Windows firewall (PowerShell as administrator):

```powershell
# -RemoteAddress and -Profile matter: without them the rule applies on ANY
# network, even the "Public" profile — and Ollama has no authentication.
New-NetFirewallRule -DisplayName "Ollama" -Direction Inbound -LocalPort 11434 `
  -Protocol TCP -Action Allow -RemoteAddress <DOCKER-HOST-IP> -Profile Private
```

Done — no WSL, no port proxy, and Ollama starts automatically with Windows.

**Note on the bundled NGINX config:** the configuration from §6 assumes, for `ollama-ws.heim.lan`, the SSH-tunnel model from §5 (macOS) and hardcodes `proxy_pass` to `127.0.0.1:11435`. Anyone exposing the workstation directly like this instead has to change the `ollama-ws` server block by hand to `proxy_pass http://<WORKSTATION-IP>:11434;` — the firewall rule above (only `<DOCKER-HOST-IP>`, "Private" profile) then remains the only access barrier on the workstation itself.

### macOS: Mac as workstation

A Mac (e.g. a MacBook Pro with plenty of RAM) works just as well as an on-demand workstation. Ollama does **not** bind to `0.0.0.0` for this — Ollama has no authentication whatsoever, and bound to `0.0.0.0` the notebook would listen on every network it joins, including café or hotel Wi-Fi. Instead, Ollama stays strictly on `127.0.0.1`, and an **SSH reverse tunnel** exposes exactly that one port, in a targeted way, on the Docker host — there too only on its own loopback, where NGINX (§6) picks it up behind an IP allowlist and basic auth.

**1. Hardwire the local Ollama to loopback:** the bundled LaunchAgent [`scripts/launchd/de.heim-ki.ollama-ws.plist`](scripts/launchd/de.heim-ki.ollama-ws.plist) binds `OLLAMA_HOST` fixed to `127.0.0.1:11434` — nothing left to replace here:

```bash
brew install ollama    # just the binary — do NOT also run "brew services start ollama",
                       # or two instances will fight over port 11434

mkdir -p ~/Library/LaunchAgents /opt/heim-ki/logs
cp scripts/launchd/de.heim-ki.ollama-ws.plist ~/Library/LaunchAgents/
launchctl load -w ~/Library/LaunchAgents/de.heim-ki.ollama-ws.plist
```

**2. Generate a key pair for the tunnel** (on the workstation):

```bash
ssh-keygen -t ed25519 -f ~/.ssh/id_ollama_tunnel -N ""
```

**3. Record the Docker host's host key** — and check the fingerprint, otherwise something on the LAN could impersonate the Docker host:

```bash
ssh-keyscan <DOCKER-HOST-IP> >> ~/.ssh/known_hosts
```

Compare the fingerprint against `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` **on the Docker host**.

**4. On the Docker host**, create a dedicated, heavily restricted system account for the tunnel:

```bash
sudo useradd --system --create-home --shell /usr/sbin/nologin ollama-tunnel
sudo -u ollama-tunnel mkdir -p ~ollama-tunnel/.ssh
sudo -u ollama-tunnel tee ~ollama-tunnel/.ssh/authorized_keys <<'EOF'
restrict,port-forwarding,permitlisten="127.0.0.1:11435" ssh-ed25519 AAAA... comment
EOF
sudo -u ollama-tunnel chmod 600 ~ollama-tunnel/.ssh/authorized_keys
```

`restrict` first disables everything (port, agent, X11 forwarding, PTY); `port-forwarding` is the only thing it turns back on — without this keyword the tunnel wouldn't come up at all, because `permitlisten` only restricts, it doesn't enable anything. `permitlisten` limits the remote forward (`-R`) to exactly `127.0.0.1:11435`. `nologin` is unproblematic because `ssh -N` never starts a shell.

**Residual risk:** `port-forwarding` re-enables every forward type, including local (`-L`) and dynamic (`-D`) forwards — `permitlisten` only restricts the remote listener, not the forward direction. A compromised tunnel key therefore still allows pivoting from the Docker host; there is no per-key option in `authorized_keys` that closes this. Anyone who wants to close it as well can optionally add to the Docker host's `sshd_config`:

```
Match User ollama-tunnel
    AllowTcpForwarding remote
    PermitListen 127.0.0.1:11435
    AllowAgentForwarding no
    X11Forwarding no
    PermitTTY no
```

`AllowTcpForwarding remote` is the first-class mechanism that allows exactly `-R` and excludes `-L`/`-D`. The tunnel also works without this Match block — it only closes the pivoting risk mentioned above.

**5. Install the tunnel agent on the workstation** ([`scripts/launchd/de.heim-ki.ollama-tunnel.plist`](scripts/launchd/de.heim-ki.ollama-tunnel.plist), replace `DOCKER-HOST-IP` and `BENUTZER` in the file first):

```bash
mkdir -p ~/Library/LaunchAgents /opt/heim-ki/logs
cp scripts/launchd/de.heim-ki.ollama-tunnel.plist ~/Library/LaunchAgents/
launchctl load -w ~/Library/LaunchAgents/de.heim-ki.ollama-tunnel.plist
```

**6. Behavior when the notebook is absent:** if the Mac is off or away, the tunnel isn't up — `ollama-ws.heim.lan` then answers with `502 Bad Gateway`. That's intentional, not a failure.

**Beware of sleep:** A closed MacBook goes to sleep — and a sleeping Mac doesn't answer Ollama requests. For workstation use, disable sleep while on power (*System Settings → Energy*, "Prevent automatic sleeping") or use `caffeinate`.

### Windows alternative for advanced users: WSL2

If you'd rather run Ollama inside WSL2 (Ubuntu):

```bash
curl -fsSL https://ollama.com/install.sh | sh
```

For Ollama to also be reachable from the LAN (not just localhost), it must bind to all interfaces:

```bash
# In WSL, e.g. in ~/.bashrc or as a systemd override:
export OLLAMA_HOST=0.0.0.0:11434
ollama serve
```

Additionally, Windows must forward port 11434 into the WSL VM (PowerShell as administrator; find `<WSL-IP>` with `wsl hostname -I`):

```powershell
netsh interface portproxy add v4tov4 listenport=11434 listenaddress=0.0.0.0 connectport=11434 connectaddress=<WSL-IP>

# -RemoteAddress and -Profile matter: without them the rule applies on ANY
# network, even the "Public" profile — and Ollama has no authentication.
New-NetFirewallRule -DisplayName "Ollama WSL" -Direction Inbound -LocalPort 11434 `
  -Protocol TCP -Action Allow -RemoteAddress <DOCKER-HOST-IP> -Profile Private
```

**Pitfalls of the WSL path:**
- The WSL IP **changes on every Windows restart** — the `portproxy` then points into thin air and must be reset (e.g. via a scheduled task script). More elegant: on Windows 11 22H2+, enable *mirrored networking* in `.wslconfig` (`networkingMode=mirrored`), then WSL shares the Windows IP and the port proxy becomes unnecessary entirely.
- `ollama serve` in a terminal is **not a service** — close the terminal, Ollama is gone. For persistent operation in WSL, set up a systemd service (enable systemd in `/etc/wsl.conf`; the install script already creates an `ollama.service` — set `Environment="OLLAMA_HOST=0.0.0.0:11434"` there as an override).

## 6. NGINX reverse proxy: friendly names instead of ports

The clever part of this setup: instead of IP addresses and ports (`192.168.1.10:3000`, `:11434`), you get clean names on the LAN. For this, an NGINX runs directly on the Docker host — install it if it's not already there:

```bash
# Linux (Debian/Ubuntu):
sudo apt install nginx

# macOS:
brew install nginx
```

(The `sites-available`/`sites-enabled` scheme used below is Debian/Ubuntu-specific. On other Linux distributions, place the configuration in `/etc/nginx/conf.d/heim-ki.conf` instead. **macOS/Homebrew:** copy the configuration to `/opt/homebrew/etc/nginx/servers/heim-ki.conf` and start NGINX as root, because ports 80/443 are privileged: `sudo brew services start nginx`. Test/reload: `sudo nginx -t && sudo nginx -s reload`.)

NGINX then proxies:

| Name | Target |
|---|---|
| `chat.heim.lan` | Open WebUI (port 3000) |
| `ollama.heim.lan` | Ollama on the Docker host (port 11434) |
| `ollama-ws.heim.lan` | Ollama on the workstation (on demand) |

**Step 1 — DNS:** All three names must point to the IP of the Docker host. (`ollama-ws.heim.lan` also points to the Docker host — NGINX then forwards to the workstation. This way the configuration stays in one place.)

> ⚠️ **A Fritz!Box alone is not enough for this.** It only assigns names in the `<device-name>.fritz.box` pattern and supports neither custom domains like `heim.lan` nor multiple names (CNAMEs) for the same IP. Realistic options:
>
> 1. **Run Pi-hole or AdGuard Home** on the LAN (e.g. as another container on the Docker host) and enter the three names under *Local DNS Records* pointing to the Docker host's IP; then set Pi-hole/AdGuard as the DNS server in the router. The cleanest solution — and blocks ads on the side.
> 2. **A `hosts` file on every client** (Windows: `C:\Windows\System32\drivers\etc\hosts`, Linux/macOS: `/etc/hosts`): three lines with `<docker-host-ip> chat.heim.lan ollama.heim.lan ollama-ws.heim.lan`. Works immediately, but scales poorly — practically impossible on smartphones.
> 3. **Compromise without extra software:** Name the Docker host e.g. `chat` in the Fritz!Box — then the household reaches Open WebUI at `http://chat.fritz.box` (for this, add `server_name chat.fritz.box;` in the NGINX configuration, or work as `default_server`). The two Ollama API names are then unavailable; anyone who needs the APIs directly uses `<docker-host-ip>:port`.

**Step 2 — NGINX configuration:** The finished configuration is in this repo at [`nginx/heim-ki.conf`](nginx/heim-ki.conf) — before copying, replace `<LAN-CIDR>` with your own home network (e.g. `192.168.1.0/24`). The key blocks (abridged):

```nginx
# Open WebUI
server {
    listen 80;
    server_name chat.heim.lan;

    # Document upload (RAG): NGINX's default 1 MB limit isn't enough for PDFs
    client_max_body_size 100M;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        # WebSockets for the chat stream:
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_read_timeout 300s;
    }
}

# Ollama API (Docker host) — workstation block analogous, see file (proxies
# there to 127.0.0.1:11435, the SSH tunnel's target port from §5)
server {
    listen 80;
    server_name ollama.heim.lan;

    # Ollama comes with NO authentication of its own — hence an IP allowlist
    # AND basic auth (satisfy all = both are required, not just one of them):
    satisfy all;
    allow <LAN-CIDR>;
    deny  all;
    auth_basic           "Heim-KI Ollama";
    auth_basic_user_file /etc/nginx/heim-ki.htpasswd;

    location / {
        proxy_pass http://127.0.0.1:11434;
        # Don't pass credentials on to Ollama — it can't do anything with them
        # and would only log them:
        proxy_set_header Authorization "";
        # Depending on version, Ollama rejects foreign Host headers as
        # protection against DNS rebinding (403) — so send localhost, not $host.
        # Defensible ONLY because the auth_basic above sits in front of it:
        proxy_set_header Host 127.0.0.1:11434;
        proxy_read_timeout 600s;   # large models need time
        proxy_buffering off;       # token streaming
    }
}
```

**Create the basic-auth password file:** the Ollama vHosts above require basic auth in addition to the IP allowlist — set up a password file once for this:

```bash
sudo apt install apache2-utils   # package providing htpasswd (Debian/Ubuntu)
sudo htpasswd -c /etc/nginx/heim-ki.htpasswd heim-ki
sudo chown root:www-data /etc/nginx/heim-ki.htpasswd
sudo chmod 640 /etc/nginx/heim-ki.htpasswd
```

⚠️ **For this HTTP variant only:** basic auth transmits the password base64-encoded in plain text, on every request — any device sniffing traffic on the LAN then knows it. Set up §10 (HTTPS) for permanent operation; this file is meant as an intermediate step before the mkcert setup.

Install and enable:

```bash
# Linux (Debian/Ubuntu):
sudo cp nginx/heim-ki.conf /etc/nginx/sites-available/
sudo ln -s /etc/nginx/sites-available/heim-ki.conf /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx

# macOS (Homebrew):
sudo cp nginx/heim-ki.conf /opt/homebrew/etc/nginx/servers/
sudo brew services restart nginx
```

The configuration itself is identical on both systems — Open WebUI listens on `127.0.0.1:3000` and Ollama on `127.0.0.1:11434`, regardless of whether Ollama runs in a container (Linux) or natively (macOS).

**If Ollama returns `403 Forbidden` through the proxy:** That's Ollama's protection against foreign Host/Origin headers. The configuration above already works around this (`proxy_set_header Host 127.0.0.1:11434;`). `OLLAMA_ORIGINS=*` would also fix it, but it's a bad idea: it lets any web page anyone in the household opens send requests to the API. Working around the host check is only defensible here because the allowlist and basic auth sit in front of it in NGINX.

Now both Ollama APIs are reachable on the LAN under proper base URLs — exactly as described in the original post. In Open WebUI, under *Admin Settings → Connections*, both URLs (`http://ollama.heim.lan` and `http://ollama-ws.heim.lan`) can be entered as Ollama endpoints. If the workstation is off, you simply use the Docker host's models.

**Tip:** Anyone who'd rather click than write config files can use [Nginx Proxy Manager](https://nginxproxymanager.com) as a container.

**Source:** NGINX reverse proxy docs: https://docs.nginx.com/nginx/admin-guide/web-server/reverse-proxy/

## 7. Setting up RAG: Docling + ChromaDB + bge-m3

Now for the part that "grinds through everything at night": documents are converted to clean text with Docling, turned into vectors with bge-m3, and stored in ChromaDB.

### Variant A (recommended): let Open WebUI handle the RAG

Open WebUI already comes with the complete RAG pipeline built in — ChromaDB is the built-in default vector database, and Docling is officially supported as an extraction engine.

**1. Start the Docling container:** The Docling server is already included in both compose files in this repo — as the compose *profile* `rag`, so the base setup stays lean:

```bash
# Linux:
docker compose --profile rag up -d

# macOS:
docker compose -f docker-compose.macos.yml --profile rag up -d
```

Docling doesn't need a port mapping: Open WebUI reaches the container directly via the compose network at `http://docling:5001`. (By default the CPU image runs; if you want to use the GPU for faster OCR, set the CUDA variant in the `.env` — see [`.env.example`](.env.example). Note: Docling is RAM-hungry with OCR-heavy PDFs.)

**2. Configure Open WebUI** under *Admin Settings → Documents*:
- **Content Extraction Engine:** `Docling` with URL `http://docling:5001`
- **Embedding model:** engine `Ollama`, model `bge-m3`, URL `http://ollama:11434` — **on a macOS host, instead use** `http://host.docker.internal:11434` (since Ollama runs natively on the Mac there, not as a container in the compose network)

**3. Throw in documents:** In Open WebUI, under *Workspace → Knowledge*, create a collection and upload "all the docs lying around." In chat, reference the collection with `#CollectionName` — and the document AI is ready.

**Sources:**
- Open WebUI RAG docs: https://docs.openwebui.com/features/rag
- Docling Serve: https://github.com/docling-project/docling-serve

### Variant B: your own pipeline as a nightly batch job (with search as an Open WebUI tool)

If you'd rather build it as a standalone nightly job like in the original post (e.g. to automatically index an entire folder), here's the complete chain — including the part missing from the post: **hooking it up to the chats.** The architecture:

```
/srv/documents ──► rag-indexer.py ──► ChromaDB server ◄── Open WebUI tool
                   (host, nightly       (container,          "Search home
                    via systemd         profile "rag")        documents"
                    timer)                                    (in chat)
```

**1. Start the ChromaDB server:** The container is included in both compose files — in its own profile `rag-batch`, because Variant B needs Chroma but not the Docling server from Variant A:

```bash
# Linux:
docker compose --profile rag-batch up -d

# macOS:
docker compose -f docker-compose.macos.yml --profile rag-batch up -d
```

The indexer on the host reaches it at `127.0.0.1:8000`; the Open WebUI tool reaches it via the compose network at `http://chroma:8000`.

**2. Set up the indexer** ([`scripts/rag-indexer.py`](scripts/rag-indexer.py)) — with its own venv, so the scheduled call uses the same environment as the installation. On Linux everything lives under `/srv`, on macOS under `/opt/heim-ki` (on the Mac, `/srv` can't be created because of the sealed system volume):

```bash
# Linux:
sudo mkdir -p /srv/scripts /srv/dokumente
sudo cp scripts/rag-indexer.py scripts/docscan.py scripts/requirements.txt /srv/scripts/

# System account for the nightly run:
sudo useradd --system --no-create-home --shell /usr/sbin/nologin heim-ki
sudo install -d -o heim-ki -g heim-ki -m 0750 /srv/heim-ki

# /srv/scripts is deliberately owned by root: the timer executes its
# contents, and the login user must not be able to modify what root runs.
sudo chown -R root:root /srv/scripts
sudo chmod -R go-w /srv/scripts

# Build the venv with sudo, so it's also owned by root:
sudo python3 -m venv /srv/scripts/.venv
sudo /srv/scripts/.venv/bin/pip install -r /srv/scripts/requirements.txt

# Documents: the login user writes, the service reads. setgid so new files
# inherit the group; not world-readable.
sudo chown -R "$USER":heim-ki /srv/dokumente
sudo chmod 2750 /srv/dokumente
```

Put documents into `/srv/dokumente` first. `scripts/docscan.py` is new and **must** be copied along, otherwise the import in `rag-indexer.py` fails. A real test run follows further below under "3. Run it nightly" — there it starts as the `heim-ki` account via the systemd service, not via a direct Python call.

**Existing installations only:** if you set up `/srv/scripts` before this hardening pass, you need to move the indexer manifest — otherwise the next run indexes all documents again from scratch:

```bash
sudo install -d -o heim-ki -g heim-ki -m 0750 /srv/heim-ki
sudo mv /srv/rag-index-state.json /srv/heim-ki/
sudo chown heim-ki:heim-ki /srv/heim-ki/rag-index-state.json
```

```bash
# macOS (analogous paths, plus a log and backup directory for the launchd jobs;
# everything then belongs to the logged-in user, since the jobs run as
# LaunchAgents in that session — see §3, "Unattended operation". Unlike on
# Linux, there's no privilege boundary here between the login user and the
# service account to protect, since they're the same — so "$USER" is fine
# here, where it would be a mistake on Linux):
sudo mkdir -p /opt/heim-ki/scripts /opt/heim-ki/dokumente /opt/heim-ki/logs /opt/heim-ki/backups
sudo chown -R "$USER" /opt/heim-ki
cp scripts/rag-indexer.py scripts/docscan.py scripts/requirements.txt /opt/heim-ki/scripts/
python3 -m venv /opt/heim-ki/scripts/.venv
/opt/heim-ki/scripts/.venv/bin/pip install -r /opt/heim-ki/scripts/requirements.txt

# Test run (put documents into /opt/heim-ki/dokumente first):
DOCS_DIR=/opt/heim-ki/dokumente STATE_FILE=/opt/heim-ki/rag-index-state.json \
  /opt/heim-ki/scripts/.venv/bin/python /opt/heim-ki/scripts/rag-indexer.py
```

The script is designed for continuous operation: it skips unchanged files (SHA-256 manifest, path configurable via `STATE_FILE`), removes chunks for deleted or changed files, embeds chunks *with* heading context (`chunker.contextualize`), and doesn't abort the whole run on a single broken file. Paths and URLs are configurable via environment variables (see the script header).

**3. Run it nightly:**

*Linux* — as a systemd timer ([`scripts/systemd/`](scripts/systemd/)); thanks to `Persistent=true` it also catches up on missed runs, and logs go to journald:

```bash
sudo cp scripts/systemd/rag-indexer.{service,timer} /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now rag-indexer.timer

# View logs:
journalctl -u rag-indexer.service
```

**Test run:** `sudo systemctl start rag-indexer.service`, then `journalctl -u rag-indexer.service -n 50` — this starts the service including all the sandbox directives from the unit (`ProtectSystem=strict` etc.) and therefore also surfaces errors caused specifically by that sandbox; calling it directly via `sudo -u heim-ki /srv/scripts/.venv/bin/python /srv/scripts/rag-indexer.py` bypasses the unit entirely and would not show such errors.

On the very first run, Docling downloads its layout/table models (and, depending on the installed version, RapidOCR or EasyOCR models) from HuggingFace — this noticeably takes a while. Thanks to `HOME`, `HF_HOME`, and `XDG_CACHE_HOME` in the unit, they land under `/srv/heim-ki` rather than in a `$HOME` that doesn't even exist for the system account (`--no-create-home`) — which is why `/srv/heim-ki` must already be owned by `heim-ki` (done above via `install -d -o heim-ki -g heim-ki`). Known limitation: should a future docling version instead want to write package-relatively into the venv, that would still fail under `ProtectSystem=strict` — this needs to be checked on the first run with whichever docling version is actually installed.

(If you prefer cron: `0 2 * * * sudo -u heim-ki /srv/scripts/.venv/bin/python /srv/scripts/rag-indexer.py >> /var/log/rag-indexer.log 2>&1` — this then runs without the systemd sandbox from the `.service` file, though.)

*macOS* — as a launchd job ([`scripts/launchd/`](scripts/launchd/)); the paths in the plist match `/opt/heim-ki`. The job deliberately runs as a **LaunchAgent in the user session** (not as a root daemon), because at 2:00 AM it needs the native Ollama and the Chroma container — and both only exist in a logged-in session with Docker Desktop/OrbStack running (→ §3, "Unattended operation": set up automatic login + "Start at login," otherwise the index run happens into thin air at night):

```bash
mkdir -p ~/Library/LaunchAgents
cp scripts/launchd/de.heim-ki.rag-indexer.plist ~/Library/LaunchAgents/
launchctl load -w ~/Library/LaunchAgents/de.heim-ki.rag-indexer.plist

# View logs:
tail -f /opt/heim-ki/logs/rag-indexer.log
```

(launchd catches up on a missed run if the Mac was merely asleep at the scheduled time — but not after a full shutdown or without a logged-in session.)

**4. Hook up search in Open WebUI:** Paste the contents of [`tools/heim_docs_suche.py`](tools/heim_docs_suche.py) into Open WebUI under *Workspace → Tools → +* as a new tool and save it. Then enable the tool for the desired model (*Admin Settings → Models → Edit Model → Tools*) or toggle it on in chat via the ⊕ menu. URLs, the collection, and the number of results can be adjusted via the tool's *Valves*.

**5. Use it:** In chat, simply ask about the contents of your own documents ("What does my lease say about the notice period?") — the model calls the tool, which retrieves the matching text passages, along with source references, from the nightly index.

> **Note:** Variant B deliberately does *not* use Docling Serve from Variant A, but rather the Docling Python library directly inside the indexer — hence the separate compose profiles: `rag` starts Docling (Variant A), `rag-batch` starts Chroma (Variant B). Both variants can also run in parallel.

**Sources:**
- Docling docs: https://docling-project.github.io/docling/
- ChromaDB docs: https://docs.trychroma.com
- Ollama embeddings: https://docs.ollama.com/api

## 10. HTTPS on the LAN

HTTPS on the LAN is more than cosmetic: without a secure context, browsers block **microphone access** — Open WebUI's voice input/output simply doesn't work over `http://` from other devices. It also gets rid of the "Not secure" warnings in the address bar, which in a family setting only raise questions.

The approach uses [mkcert](https://github.com/FiloSottile/mkcert): a small private certificate authority (CA) on the Docker host that issues certificates for the three `.lan` names.

**Step 1 — create the CA and issue a certificate** (on the Docker host):

```bash
sudo apt install mkcert libnss3-tools    # Linux
brew install mkcert nss                  # macOS ("nss" only needed for Firefox)

mkcert -install        # creates the local CA and registers it on THIS machine

# One certificate for all three names:
mkcert chat.heim.lan ollama.heim.lan ollama-ws.heim.lan

# Linux:
sudo mkdir -p /etc/nginx/certs
sudo cp chat.heim.lan+2.pem     /etc/nginx/certs/heim-ki.pem
sudo cp chat.heim.lan+2-key.pem /etc/nginx/certs/heim-ki-key.pem

# macOS (Homebrew NGINX):
sudo mkdir -p /opt/homebrew/etc/nginx/certs
sudo cp chat.heim.lan+2.pem     /opt/homebrew/etc/nginx/certs/heim-ki.pem
sudo cp chat.heim.lan+2-key.pem /opt/homebrew/etc/nginx/certs/heim-ki-key.pem
```

**Step 2 — switch NGINX to HTTPS:** The finished configuration is at [`nginx/heim-ki-https.conf`](nginx/heim-ki-https.conf) — it redirects port 80 to 443 and **replaces** the HTTP variant:

```bash
# Linux (Debian/Ubuntu):
sudo cp nginx/heim-ki-https.conf /etc/nginx/sites-available/
sudo rm -f /etc/nginx/sites-enabled/heim-ki.conf
sudo ln -s /etc/nginx/sites-available/heim-ki-https.conf /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx

# macOS (Homebrew): adjust the certificate path in the file to /opt/homebrew/etc/nginx/certs,
# then:
sudo rm -f /opt/homebrew/etc/nginx/servers/heim-ki.conf
sudo cp nginx/heim-ki-https.conf /opt/homebrew/etc/nginx/servers/
sudo nginx -t && sudo brew services restart nginx
```

**Step 3 — install the CA on family devices.** This is the price of LAN HTTPS: every device has to trust your own CA once. The CA file is at `$(mkcert -CAROOT)/rootCA.pem` — **only distribute `rootCA.pem`, never `rootCA-key.pem`!**

- **Windows:** double-click `rootCA.pem` → *Install Certificate* → store location *Trusted Root Certification Authorities*.
- **Android:** copy the file to the device → *Settings → Security → Install a certificate (CA certificate)*.
- **iOS/iPadOS:** open `rootCA.pem` e.g. via AirDrop/Mail → install profile → additionally enable it under *Settings → General → About → Certificate Trust Settings*.
- **macOS/Linux:** import into the keychain or system trust store; Firefox manages its own store (*Settings → Certificates → Import*).

**Alternative:** If you'd rather use [Caddy](https://caddyserver.com) as a container instead of the host NGINX, `tls internal` gets you the same thing automatically (Caddy brings its own CA) — distributing the CA file to devices is still necessary there too.

## 11. Backup & Restore

What needs to be backed up is anything that can't be recreated: the **Open WebUI volume** (users, chats, knowledge collections), the **Chroma volume** (RAG index from Variant B), and the indexer manifest. The Ollama models are deliberately excluded — `ollama pull` can always fetch them again.

The script [`scripts/backup.sh`](scripts/backup.sh) does exactly that (including cleaning up old backups, default: 14 days) and runs daily at 3:30 AM — after the RAG indexer. To tar up the volumes it starts a small Alpine container; the image is pinned to a fixed digest via `ALPINE_IMAGE` (overridable via environment variable), so a fresh, unvetted `:latest` image isn't pulled on every run.

*Linux* — via a systemd timer:

```bash
sudo mkdir -p /srv/scripts    # already exists if §7 Variant B was set up
sudo cp scripts/backup.sh /srv/scripts/
sudo chown root:root /srv/scripts/backup.sh
sudo chmod 755 /srv/scripts/backup.sh
sudo cp scripts/systemd/heim-ki-backup.{service,timer} /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now heim-ki-backup.timer

# Run manually / view logs:
sudo systemctl start heim-ki-backup.service
journalctl -u heim-ki-backup.service
```

The backup deliberately stays root, because it needs the Docker socket — the docker group would be root-equivalent anyway, so it wouldn't be a real gain. The actual protection is that `/srv/scripts` is owned by root (§7): the login user can't modify `backup.sh`, even though the script itself runs with root privileges.

*macOS* — via a launchd job ([`scripts/launchd/de.heim-ki.backup.plist`](scripts/launchd/de.heim-ki.backup.plist), target `/opt/heim-ki/backups`). This job also runs as a **LaunchAgent in the user session**, because the docker CLI can only reach the Docker Desktop/OrbStack daemon there (the socket is at `~/.docker/run/docker.sock`, not `/var/run/docker.sock`). If Docker isn't reachable at night, `backup.sh` aborts with an error instead of silently writing an empty backup — so for reliable nightly runs, set up §3, "Unattended operation":

```bash
# Directories already exist if §7 Variant B was set up — otherwise:
sudo mkdir -p /opt/heim-ki/scripts /opt/heim-ki/logs /opt/heim-ki/backups
sudo chown -R "$USER" /opt/heim-ki

cp scripts/backup.sh /opt/heim-ki/scripts/ && chmod +x /opt/heim-ki/scripts/backup.sh
mkdir -p ~/Library/LaunchAgents
cp scripts/launchd/de.heim-ki.backup.plist ~/Library/LaunchAgents/
launchctl load -w ~/Library/LaunchAgents/de.heim-ki.backup.plist

# Run manually / view logs:
launchctl start de.heim-ki.backup
tail -f /opt/heim-ki/logs/backup.log
```

The target directory is `/srv/backups/heim-ki` or `/opt/heim-ki/backups` (changeable via `BACKUP_DIR` — ideally a NAS mount, so the backup doesn't live on the same disk as the data).

**Restore** (example: Open WebUI volume; analogous for `chroma-data` — macOS: `docker compose` each with `-f docker-compose.macos.yml` and the backup path `/opt/heim-ki/backups`):

```bash
docker compose down
docker run --rm -v open-webui-data:/data -v /srv/backups/heim-ki:/backup alpine \
  sh -c "rm -rf /data/* && tar xzf /backup/open-webui-data-YYYY-MM-DD.tar.gz -C /data"
docker compose up -d
```

## 12. Wake-on-LAN for the workstation

So the workstation with the big GPU doesn't have to run continuously, you can wake it on demand from the LAN:

**One-time setup on a Windows workstation:**
1. Enable "Wake on LAN" (or similar) in the **BIOS/UEFI**.
2. In Windows, in **Device Manager**, under the network adapter's *Power Management*, enable "Allow this device to wake the computer" and under *Advanced*, enable "Wake on Magic Packet."
3. **Disable Windows Fast Startup** (*Power Options → Choose what the power buttons do*) — with Fast Startup active, "Shut down" is a hybrid state from which WoL often doesn't work.
4. Note the **MAC address**: `ipconfig /all` → "Physical Address."

**For a Mac as a workstation:** In *System Settings → Energy* (or *Battery → Options*), enable "**Wake for network access**" — this wakes the Mac from **sleep** (not from a powered-off state; Macs don't support WoL from shutdown). Works reliably over Ethernet; with Wi-Fi-only operation it's a matter of luck. MAC address: *System Settings → Network → Details*.

**Waking from the Docker host** with [`scripts/wol.sh`](scripts/wol.sh):

```bash
sudo apt install wakeonlan     # Linux
brew install wakeonlan         # macOS host

./scripts/wol.sh AA:BB:CC:DD:EE:FF
```

A minute later, the workstation's Ollama is available at `ollama-ws.heim.lan` (the native app starts automatically with Windows; on the Mac the LaunchAgent from §5 takes care of it). **Tip:** A Fritz!Box can also do this without a script — in the device details under *Home Network → Network* there's a "Start computer" button.

## 13. Troubleshooting

| Symptom | Cause & fix |
|---|---|
| Containers don't see the GPU | Test: `docker run --rm --gpus all nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi`. If that fails: `sudo nvidia-ctk runtime configure --runtime=docker && sudo systemctl restart docker`. After a driver update: restart the host. |
| Responses suddenly very slow | `docker exec ollama ollama ps` shows whether the model is (partially) running on the CPU (`XX%/YY% CPU/GPU`). Fix: a smaller/more heavily quantized model, or the §4 tips (`OLLAMA_MAX_LOADED_MODELS=1`). |
| First prompt "hangs" | The model is currently being loaded into VRAM — this takes a while for larger models. `OLLAMA_KEEP_ALIVE` (§4) prevents frequent reloading. |
| `403 Forbidden` from `ollama.heim.lan` | Ollama's Host header protection — the §6 configuration therefore sends `Host 127.0.0.1:11434`; check whether the repo's configuration is really active (`nginx -T \| grep -A5 ollama`). |
| Upload fails with `413 Request Entity Too Large` | `client_max_body_size` missing/too small — included in `nginx/heim-ki.conf` (100 MB), reload NGINX. |
| Docling container crashes / host swaps on large PDFs | Docling OCR is RAM-hungry. Split large scans, or give the service a `mem_limit` in the compose file; if needed, upload documents one at a time. |
| `ollama-ws.heim.lan` dead after a Windows restart (WSL path) | The WSL IP has changed — reset the port proxy, or switch to *mirrored networking* or the native app (§5). |
| "Home Documents" tool finds nothing | Is Chroma running? (`docker ps` → `chroma (healthy)`; a plain `docker compose ps` only shows profile services like `chroma` with `--profile rag-batch` — and on macOS only with `-f docker-compose.macos.yml`). Did the indexer write anything? (Linux: `journalctl -u rag-indexer.service`, macOS: `/opt/heim-ki/logs/rag-indexer.log`). Do the collection name and `chroma_url` in the tool's valves match? |
| macOS: Ollama painfully slow, Mac fan spinning | Is Ollama accidentally running as a container? On macOS, containers have **no GPU access** — Ollama must run natively (`brew services start ollama`, §3) and Open WebUI must point to `host.docker.internal:11434` via `docker-compose.macos.yml`. |
| macOS: Open WebUI can't reach Ollama | Is native Ollama running? (`ollama ps`, `brew services list`). The Open WebUI *Connections* must contain `http://host.docker.internal:11434`, not `http://ollama:11434` — there's no Ollama service name in the macOS compose file. |
| macOS: nightly jobs (indexer/backup) didn't run | The jobs run as LaunchAgents only in a **logged-in session** with Docker Desktop/OrbStack running and the Mac awake — see §3, "Unattended operation" (auto-login, "Start at login," `pmset`). Status: `launchctl list \| grep heim-ki`; logs: `/opt/heim-ki/logs/*.log`. |
| General diagnostics | `docker compose ps` (health checks!; macOS: with `-f docker-compose.macos.yml`, profile services additionally with `--profile rag`/`rag-batch` — or simply `docker ps`), `docker logs open-webui`, `docker stats`; Linux only: `docker logs ollama`, `nvidia-smi` (macOS: Ollama native → `ollama ps`, logs via `brew services`). |

## 14. Further ideas

- **Model recommendations for 4 GB VRAM:** `llama3.2:3b`, `qwen2.5:3b`, `phi3:mini` — all in the [Ollama Library](https://ollama.com/library).
- **Access from outside the home:** instead of port forwarding, use a VPN into the home network — the Fritz!Box supports WireGuard directly, or alternatively [Tailscale](https://tailscale.com). This keeps the home AI reachable on the go without exposing anything to the internet.
